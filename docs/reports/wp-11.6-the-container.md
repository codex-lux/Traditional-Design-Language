# WP-11.6 — The container: teaching six layers that a house can be two rectangles

*Phase 11, package 6 of 11. 4 September 2026. From
`oq/a-massing-element-is-placed-and-nothing-below-the-placer-knows-it`, ruled the same day, and
`docs/reports/tidewater-layout-diagnosis-2026-09-04.md` Part V, which finds the container to be the
root of twenty-two of its fifty-one findings.*

**IN PROGRESS — layers 1 through 5 of 6.** The ruling's operative half is an order and an instruction to
measure after each step, so this report is written the same way and grows a section per layer.

## The instrument first, and two of its probes were wrong

The ruling says the disclosure "names six layers today and must name five, then four, then none —
a falling count, in the record, is how this ruling is checked rather than claimed". A falling count
is only evidence if the underlying defect is measured independently, so it is:

| layer | probe | baseline |
|---|---|---|
| openings | dependency openings refused | **9 of 14** |
| structure | dependency partition inside the main wall set / the dependency's own envelope walls | **1 / 0 of 2** |
| vertical_score | upper edges credited to a dependency-only wall line | **0 — NOT REPRODUCED** |
| lot_cap | built extent over the lot, uncapped | **24 ft over an 80 ft lot, `lot_capped: null`** — CORRECTED at layer 4: the true reading is `false`, and the probe had read `footprint.lot_capped`, which does not exist |
| plan_check.drawn | dependency rooms convicted of reaching no exterior wall | **2** |
| export_ifc | dependency rooms off the slab | **3** |

The fixture is the Tidewater plan with its kitchen, pantry and breakfast room tagged into a west
dependency — `tests/test_geometry.py`'s own fixture, deliberately, because two files measuring two
different dependencies would be two houses.

**THREE PROBES OF SIX WERE WRONG, AND THE THIRD WAS ONLY FOUND AT ITS OWN LAYER.** Two read
zero on the first run and neither zero was a defect's absence; the third read a plausible `null`
off a key that does not exist and was believed until its own layer, three commits later.

**TWO PROBES READ ZERO ON THE FIRST RUN AND NEITHER ZERO WAS A DEFECT'S ABSENCE.** The openings
probe looked for a window drawn far from its room and found none, because the real defect is a
window **refused outright** — every dependency opening came back *"the placement puts this room on
no such boundary wall"*. The structure probe read a `bearing_lines_x` key that does not exist; the
section carries `walls` with a `position_ft`, and a missing key returns nothing. **A probe pointed
at the wrong defect and a probe reading a missing key both report 0, and 0 reads as
nothing-wrong** — the same shape as the stacking meter's missing `vertical` key one package
earlier, twice in two packages.

Two of the six still read zero and both say why rather than counting as clean: the lot probe reads
0 honestly on the reference plan's own 140 ft lot, where the 104 ft built extent fits, and needed
an 80 ft lot to fire; `vertical_score`'s defect does not reproduce on this fixture at all, because
no upper room's edge falls within 0.75 ft of a dependency line, and it is recorded as **NOT
REPRODUCED** rather than as absent.

## Layer 1 — `openings`

**First, and not by preference.** The ruling: an element-aware `openings` makes the dependency's
windows real, which turns `structure`'s missing envelope walls into a **drawn collision** rather
than a silent absence. Fixing them the other way round leaves the shield in place — WP-7.4's
fixture packer, where turning the corner produced five overlapping pairs immediately because the
fixtures had previously been wrong together.

`openings.envelopes()` maps each room to its own element's rectangle and `_boundary_walls` tests
against that instead of the main block. Refused dependency openings **9 → 5**.

**The five that remain are honest.** The kitchen's north edge is 23.72 against its element's 29.12:
it does not reach that face and the refusal is correct. That is the difference between a house
telling you something and an instrument telling you about itself.

**THE OLD READING DID NOT LOSE THE DEPENDENCY'S WALLS — IT ASSERTED ONE FORTY-ONE FEET AWAY.**
`x <= tol` is satisfied by any x at or west of 0.6, so a room at x = −41 tested as sitting on the
main block's **west face**. Against the main block the fixture's kitchen returns `{"W": (9.05,
23.72)}`, not `{}`. That is the mechanism behind the entry's *"a window drawn fourteen feet from
the room"*, and it is worse than reporting nothing: a false positive rather than a silence. This
report's first draft asserted the old call returned nothing, and the test that pinned it failed —
which is the only reason the sharper statement is here.

**The join is the room's own `block` tag, not a room list on the block.** `blocks_record` writes
id, role, x, y, width, depth and area and **no membership**, so a first version read `b["rooms"]`,
found nothing on every plan, and left all nine refusals in place while reporting success. The tag
is what the placer itself groups on, so reading it keeps one spelling of what an element contains.

**The one-rectangle regression holds by construction.** `envelopes()` returns an empty map below
two elements, so every caller falls back to the main block. Both shipped plans place identically —
scores 685.3 and 592.3, declared stacking claims and transfer counts unmoved.

**The disclosure is at five**: `structure`, `vertical_score`, `lot_cap`, `plan_check.drawn`,
`export_ifc`.

## Layer 2 — `structure`

**One structure per element.** `build_section` runs `wall_lines`, `bearing_lines` and `span_check`
once per element over that element's own rooms, at that element's own origin, and tags each wall
and span with the element it belongs to. A one-element plan takes the same path with one element,
so the sixteen one-rectangle records are byte-identical by construction rather than by a branch.

| | before | after |
|---|---|---|
| walls tagged `main` outside the main block | **1** (a dependency partition at x −23.3 on a 0–63 block) | **0** |
| the dependency's own envelope walls | **0 of 2** | **2 of 2** |
| spans computed across the gap | possible | **impossible by construction** |

**A span is not filtered out of the gap — it cannot be computed there**, because each element's
`span_check` sees only its own bearing lines and breaks on its own two edges rather than on 0 and
its width.

**AND THE DEPENDENCY'S OWN STRUCTURE IS JUDGED FOR THE FIRST TIME AND IMMEDIATELY FAILS**: 27.0 ft
and 20.07 ft against a 20 ft hand-framed capacity. That is the shield lesson arriving exactly as
the ruling predicted. A silence became a finding, which is the whole point of modelling it.

The one-rectangle regression holds to the digit: the Tidewater plan still reports a worst span of
53.94 ft, the spec Colonial still none, and neither record grows an `element` key.

**The disclosure is at four**: `vertical_score`, `lot_cap`, `plan_check.drawn`, `export_ifc`.

## Layer 3 — `vertical_score`, and the entry's own description of it was half wrong

**The support credit the entry named CANNOT FIRE.** It says an upper wall within 0.75 ft of a
dependency wall line scores as *"continues to a wall below, where there is no upper floor at all"*.
`blocks_for` lays only level 0 into elements, so every upper room is inside the main block and
every dependency line is outside it. Measured on the fixture rather than reasoned: ground x lines
run `[-41.0, -23.3, -14.0, 0, 27, 36.05, 45.05, 51.13, 63.0]`, upper x lines run
`[0, 18, 36.0, 45.0, 51.1, 57.6, 63.0]`, and **no upper edge is within 0.75 ft of any
dependency-only line** — the nearest is 14 ft away, which is the hyphen's own default gap.

That is recorded rather than fixed, and pinned: if the placer ever lays an upper level into an
element, the test goes red and the claim becomes real.

**What WAS reachable is the opposite sign.** A `stacks_over` claim naming a room in another element
was **charged 40 points** and told *"is drawn clear of it"* — a failure no placement this engine can
produce could avoid, phrased as a placement that went wrong. That is the OQ 52 family. It is
COULD NOT EVALUATE now, with its reason on the record. Measured: `vertical_score` **114 → 74** on a
fixture whose upper bath declares it stacks over a kitchen in the dependency.

**The check lives in the one spelling.** `declared_stack_breaks` returns both states and
`stack_breaks_only` is what a charge or a rejection may act on, so WP-11.5's hard rule and this
layer's charge cannot disagree about the same claim.

**And the wet-stack test needed no change, which was also measured.** An upper bath over a kitchen
that has moved into a detached dependency really does sit over no wet room. Tagging the service
rooms out took that finding from one to two, and both are true.

**The join is the room's own `block` tag and not `footprint.blocks`**, for an ordering reason that
cost a first attempt: `blocks_record` writes that list inside `write_record`, **after** the search
loop the map is used in, so a map built from it is empty exactly where the charge is decided.

**The disclosure is at three**: `lot_cap`, `plan_check.drawn`, `export_ifc`.

## Layer 4 — the lot cap, and its bypass was never about massing elements

**The ruling is item 2: the cap is on the BUILT EXTENT, hyphen included** — *"the hyphen is roofed
ground; a building whose covered area overruns its lot has overrun it"*. `flank_sizes` is the
sizing `blocks_for` already did, lifted out so the cap can read it without a second transcription;
`flanking_extent_ft` sums `gap + width` per element, and the hyphen is in that sum because the
ruling says so. The sizes do not depend on the main block — a dependency comes from its own rooms
over a single-pile depth — which is what makes the flank computable *before* the main block's bay
count is chosen rather than after it.

Measured on the fixture at an 80 ft lot: main block **63 → 45 ft**, built extent **104 → 86 ft**,
`lot_capped` **false → true**.

**THE BASELINE ITSELF WAS WRONG — THE THIRD PROBE OF SIX TO BE WRONG, AND THE SECOND TO READ A
KEY THAT IS NOT THERE.** The table above published `lot_capped: null`, and carries the correction
beside it now. There is no such value: `lot_capped` is a
boolean expression on both engines and can never be `None`. The probe had read
`footprint.lot_capped`, and the record carries it at `geometry_report.lot_capped`. The true reading
is **`false`** — and that is worse than the `null` it was reported as, in the direction that
matters: `null` looks like a record declining to judge, and `false` is the placer asserting *the
lot did not constrain this house* over a house 24 ft wider than its lot. **A false positive
reported as an unjudged state**, which is the OQ 52 family living in the instrument rather than in
the code.

**AND THE SECOND BYPASS IS ON EVERY PLAN IN THIS CORPUS.** Chasing the first one, the probe was run
on the same plan with **no dependency at all** — one rectangle, which is what all sixteen records
are — and the cap was bypassed there too:

| usable lot width | bays the lot holds | bays built | main block | over |
|---|---|---|---|---|
| 140 ft | 15 | 7 | 63 ft | — |
| **60 ft** | **6** | **7** | **63 ft** | **3 ft** |
| 45 ft | 5 | 5 | 45 ft | — |
| **36 ft** | **4** | **5** | **45 ft** | **9 ft** |
| **18 ft** | **2** | **5** | **45 ft** | **27 ft** |

Two different causes. At 60 ft it is the **centre-bay parity bump**: `if odd_wanted and start % 2
== 0: start += 1` made the count odd whatever the lot said. At 36 ft and below it is the
**massing's own stated minimum**: `start = max(mb["min"], from_area)` does not consult `maxbay`,
which is where the cap lives.

**And the parity bump had made a named refusal unreachable.** `bay_count_forced_even` carries the
comment *"a diagram that wanted a centre bay and did not get one is a REFUSAL, named — not a silent
six. Today the only way here is a lot too narrow to hold the odd count."* That path could not be
taken: the bump forced the count odd before the lot was consulted, and both the growth and shrink
loops step by two, so `bays % 2 == 0` was unreachable on every non-void plan. **A refusal that
cannot fire, with a comment naming the exact case it cannot fire in** — WP-8.6's subject, found
here by measuring a lot rather than by reading the line. Clamping the bump to `lot_maxbay` fires it
for the first time: 60 ft lot, **six bays and 54 ft**, `bay_count_forced_even: true`.

**The massing's floor is DISCLOSED and not capped, on purpose.** Shrinking the main block below the
count its own massing states is decision #11's ordering run backwards — compromising the diagram to
save the site — and nobody has ruled that a lot outranks a diagram's floor. So
`geometry_report.lot` reports the usable width, the main block, the flank, the built extent and the
overrun in **three states** (a plan with no lot gets COULD NOT EVALUATE and is not told it fits),
and where the residue is the massing's floor the note names the floor, the lot's count and the
question. `oq/a-lot-too-narrow-for-the-diagrams-own-minimum-bay-count`.

**A lot the flank has already eaten refuses, and the refusal says why.** *"lot too narrow: 50 ft
usable width cannot hold even this diagram's minimum 2 bays (18 ft)"* would be absurd about 50 ft
and 18 ft. It now names the 41 ft the flanking element and its hyphen take.

**The one-rectangle regression holds to the digit**: both shipped plans place identically, scores
685.3 and 592.3 — and `spec-builder-colonial` is lot-capped as shipped (50 ft on a 60 ft lot), so
the cap itself is exercised by the regression rather than merely bypassed by it.

**Six mutations, six caught**, including one that drops the hyphen from the flank, one that
re-derives a width inside `blocks_for` instead of reading `flank_sizes`, and one that collapses the
no-lot state into a pass.

**And the strongest guard is the one the extraction makes possible.** The cap computes the flank
*before* the placement and `blocks_for` lays it out *after*, so the two can be held against each
other on the placement's own output. A dependency on each side — three elements, 118 ft of building
— and `built_extent − main == flank` exactly, at 55.0 ft. A second transcription of the sizing rule
is what that test would catch.

**The disclosure is at two**: `plan_check.drawn`, `export_ifc`.

## Layer 5 — `plan_check`'s drawn layer, and the layer whose symptom had already gone

**This is the layer the package warned about four commits ago.** Teaching `openings` at layer 1
seated the dependency's windows, and `plan_check`'s landlocked test short-circuits at `if seated:
continue` — so the count of *"reaches no exterior wall"* findings fell **2 → 0** while the `touches`
arithmetic four lines below still read `fp_w`/`fp_h` and was still wrong. A meter watching the
finding would have crossed this layer off the list at layer 1. The probe drives the condition
instead: strip the placement from the dependency's windows and the test runs.

**The measurement, and the control is what makes it a fix rather than a loosening:**

| room | main-block read | element read | in |
|---|---|---|---|
| `kitchen` | `[]` — convicted landlocked | **`['S','W']`** | west-dependency |
| `breakfast` | `[]` — convicted landlocked | **`['S','E']`** | west-dependency |
| `chamber2` | `[]` | `[]` | main |
| `stair` | `[]` | `[]` | main |

The two dependency rooms lose a false conviction; the two rooms that really are in the middle of
the house keep theirs. A change that had moved all four would have been a check being switched off.

**The finding they take instead names the element**, and where a wall of that element looks across
the gap it says what that means. `openings.faces_across_a_gap` returns `{face: neighbour_element}`;
on this fixture the dependency's east face returns `{'E': 'main'}`, so the breakfast room reads:

> *Breakfast Room is drawn with no window: it stands on the S/E wall(s) of the west-dependency
> element … **Its E wall(s) are exterior to the weather and interior to the view: they look across
> the gap at the main element.***

That is ruling 4's second half, and it is **reachable on this fixture rather than recorded as
unreproduced** — the layer-3 outcome, which is worth contrasting. The kitchen's south and west
faces look at open ground and take no note, which is what makes it a discrimination rather than a
decoration.

**The diagonal case is refused rather than modelled**, as the ruling says, and the refusal is one
condition: a face counts only when the other element overlaps it on the perpendicular axis. A block
past the corner is yard.

**`envelopes` is layer 1's map, not a second spelling of the `block`-tag join**, and the element id
comes through `geometry.is_block_tag` — the predicate that exists because three places ask this
question and two of them answering differently is how a plan gets refused by one layer for an
element another layer does not build.

**The one-rectangle regression is pinned at its strongest form**: not a count but a digest over
every finding's kind, room and statement. Both shipped plans are identical before and after —
`4ec3f784caa5a095` and `433325b5299ea477`.

**Seven mutations, seven caught**, including one that returns `touches` to the main block, one that
calls every touched wall gap-facing, one that lets a diagonal neighbour count, and one that drops
`export_ifc` from the disclosure without teaching it.

**The disclosure is at one**: `export_ifc`.

## The finding a symptom-watching meter would have got wrong

**Teaching `openings` made `plan_check`'s landlocked finding disappear without fixing
`plan_check`.** That test short-circuits at `if seated: continue` — it runs only on a room whose
windows are ALL unplaced. Seating the dependency's windows took the count of *"reaches no exterior
wall"* findings from **2 to 0**, while the `touches` arithmetic four lines below still read
`fp_w`/`fp_h` and was still wrong.

A meter watching the finding would have reported layer 5 taught, by accident, two layers early. The
probe drives the condition instead: strip the placement from the dependency's windows and the layer
convicts **2** rooms, one of them a kitchen sitting on its own element's south and west faces. So
`plan_check.drawn` stays in the disclosure, correctly, and a test pins both halves — the symptom
absent as shipped, the layer still wrong when reached.

**This is the third probe in one package that had to be corrected**, after one pointed at the wrong
defect and one reading a key that does not exist. All three would have reported a clean zero.
