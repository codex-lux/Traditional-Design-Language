## I. What was asked, and what was built

Brief → candidates → plan → drawings → export was spread over three rail groups with static
metas and one sentence on the Overview naming the order. A reader on the Drawing Set could not
tell that the house in front of them had been refused, that the compose it came from had failed,
or which candidate the bench's plan even was. §G gave that a pure reading (`journey/journey.js`,
built by WP-14.6); this package draws it and makes the session hold the two facts it needs.

- **`components/JourneyBar.jsx`** — one bar, mounted once by `App.jsx` above `<main>` on the six
  house surfaces (brief, candidates, workbench, drawings, export, transcription) and never in full
  screen. A `nav` labelled *house journey*; each step an anchor carrying `data-step`, the current
  one `aria-current="step"`; the state words stand OUTSIDE the anchor, so a glossary `Term`
  (refused, fatal, serious, unjudged) is never inside a link. A blocked step is a
  `<span data-step data-blocked>` and never an anchor. Next is an anchor only where the step can
  proceed; otherwise it is the journey's own reason. The provenance line names the plan on the
  bench and links back to where it came from.
- **`journey/bar.js`** — the bar's own decisions as pure functions: where it is shown
  (`showJourneyBar`), which step is a link, which is blocked, what Next offers, and whether the
  origin may be linked (`barView`). A step made FROM the plan (drawings, export) is a link only
  while the step before it can proceed, so a refused house shows *blocked: refused* on both and no
  link to a drawing the refuse-to-draw contract forbids is on the page to be followed. A plan from
  an EARLIER compose names its candidate and does not link, because the Candidate Set shows the
  session's current job, which would be somebody else's candidate.
- **`journey/sessionWrites.js`** — every write the journey's reading depends on, pure:
  `composeHandlers` (the ONE handler set both compose streams hand `jobEvents`), `reattach`,
  `jobExpired`, `composeStart`, `planFromOf`, `briefNameOf`, and the two sanitisers that read
  `planFrom` and `jobError` back from storage.
- **`state/session.js`** — `planFrom` and `jobError` per §G.1; the persisted object is
  `{ brief, jobId, planFrom, jobError }` under the unchanged `'tdl-workbench-session'` key;
  `recordPlanFrom(kind, plan, extra)` is the one writer the three surfaces call.
- **`journey/briefForm.js`** and **`surfaces/BriefIntake.jsx`** — step one, which is where the
  journey broke (§II.1). The budget tiers are the brief schema's own enum; the style is chosen with
  the `StylePicker` every other surface uses and is never a constant; `?style=` seeds it and
  `?example=<name>` loads a shipped brief by name and then leaves the address; Compose is a real
  `<button>`, disabled until the brief states the two fields its schema requires, and that test
  is the journey's own brief step rather than a second spelling of it.
- **`surfaces/CandidateSet.jsx`** — its reattach stream records a failure, releases its
  `EventSource` when the surface goes away, and opening a candidate records `planFrom`.
- **`surfaces/PlanWorkbench.jsx`** and **`surfaces/Transcription.jsx`** — one import and one
  changed line each: the example load and "send to the bench" record where the plan came from.
- **`App.jsx`** — the import and the mount.

## II. What was found

**1. STEP ONE REFUSED THREE OF ITS FOUR OWN BUDGET CHOICES.** `BriefIntake.jsx` offered
`entry`, `move-up`, `custom` and `estate`; `schema/brief.schema.json` admits `value`, `mid`,
`custom` and `unlimited`. Re-derived here with `jsonschema` on `briefs/family-georgian.json`:
`entry`, `move-up` and `estate` are REFUSED (*"is not one of ['value', 'mid', 'custom',
'unlimited']"*), `custom` is admitted. `jobs.submit` validates the brief before a job exists, so
a reader who chose any of the three was told the whole brief was refused. The form now reads the
enum from `GET /api/schema/brief` (`briefForm.budgetTiers`); a tier an older persisted draft
carries that the schema does not admit is SHOWN as off the schema rather than silently dropped
from the reader's brief (`offSchemaTier`).

**2. A REFUSED BRIEF ERASED THE LAST GOOD RESULT.** `compose()` did
`session.set({ result: null, progress: [] })` BEFORE `api.compose`, so a brief the server refused
at submit wiped the candidates the previous brief had produced. `composeStart(job_id)` is written
only once the server has accepted the job; a refused brief now leaves the last candidates
standing, which is what they still are.

**3. A FAILED COMPOSE WAS REPORTED NOWHERE, BY TWO DEFECTS THAT HID EACH OTHER.** Brief Intake's
stream was the one that looked at `error` — into its own component state — and `compose()` calls
`go('candidates')` immediately, so that stream was closed by Brief Intake's own unmount effect
(the leak fix an earlier adversarial audit made there, whose comment says exactly this) as soon as the navigation rendered —
before a compose of any length could report anything. The stream that actually listened was the Candidate Set's reattach, whose `error`
was `() => {}`; and a job the server had already failed (`api.job` status `error`) was forgotten
with `session.set({ jobId: null })`, its reason discarded. Either way the Candidate Set read the
job as gone or still composing. `composeHandlers` writes `jobError {state: 'failed', reason,
jobId}` on the stream's `error` for both sites; `reattach` writes it from `api.job`'s own error;
a 404 is `expired`, named, rather than a silent forget.
**The guard that existed could not see it**: `sse_handlers.test.mjs` read each call site's handler
KEYS and asserted every compose event was registered — and `error: () => {}` registers `error`.
A key that is present and does nothing IS the defect. The file now holds both call sites to
`composeHandlers(session, <job id>)` with nothing spread over it, and DRIVES the handler set
(what each handler writes), which is what the mutations below bite on.

**4. EVERY VISIT TO THE CANDIDATE SET DURING A COMPOSE LEAKED A STREAM.** The reattach called
`jobEvents(...)` for its side effect and discarded the handle, so nothing could close it; a
reader moving between the bench and the Candidate Set during a long compose opened a new
`EventSource` each time, against a browser's six per origin. Brief Intake had already learned
this and closes its own. The handle is kept and the effect's cleanup releases it; a source guard
in `sse_handlers.test.mjs` says so, and says that it is a reading of source (a React effect
cannot be driven under `node --test`).

**5. THE BRIEF WAS NAMED BY ITS CITATION.** The Candidate Set's eyebrow printed `result.brief` —
`brief:family-georgian` on the shipped example — because the result carries the citation and not
the name. `briefNameOf(result, brief)` reads the name the brief itself states, falling back to the
id in a code span. **Two neighbours of this are not in this package's files and are named for the
lead**: `routeCite('brief:x')` (`citations.js`) discards the id and lands on a bare Brief Intake,
so a brief citation reaches no brief; and `RecordLink` prints a `brief:` citation raw, because the
search index carries no briefs to name it from.

**6. THE JOURNEY CANNOT ATTRIBUTE AN EVALUATION WHOSE CHECK ERRORED, AND THE BAR IS WHERE THAT
BECOMES VISIBLE.** WP-14.6's §III.1 found it in the pure module and wrote it down before any
surface drew the bar: `core.check_plan`'s two error payloads carry no plan id, so on a record
whose check errored and whose placement was refused, the journey reads the plan as *not yet
evaluated* and the drawings and export steps as *ready*, and the bar makes both links. **Measured
here, the shipped corpus does not reach it today**: AUTO_RESULT. The fix is a server line and a
journey line and the server is outside this package's files; writing the journey half alone would
read a key nothing writes. Filed as `oq/an-evaluation-whose-check-errored-names-no-plan`.

**7. `planFrom` IS RECORDED BY THE THREE WRITERS §G.1 NAMES AND NO OTHER, AND THE IDENTITY RULE
KEEPS THE REST HONEST.** A pasted record, an undo, and Transcription's DXF-complete load (which
loads the bench directly rather than through *send to the bench*) do not write it. §G's rule —
`planFrom` counts only when `planFrom.planId === plan.id` — makes a record with another id read
*origin not recorded*, which is true. The limit is a paste that keeps the SAME id as an example
the reader loaded earlier: it inherits *an example*. That is one line per path and each is in a
file this package may change by two lines at most; it is named rather than spent.

## VI. Deviations from the brief, stated

- **`journey/journey.js` gains one word**, `next`, in `JOURNEY_WORDS`. The bar's Next link needs a
  word and the rule is that every word is a glossary record's or the journey's; adding it to the
  journey's own table is the one place it may live. The file is WP-14.6's.
- **`App.jsx` is two hunks, not one**: the import at the head of the file and the mount above
  `<main>`. A mount cannot be written without its import.
- **`jobError.reason` may be `null`**, where §G.1 types it `string`: an `error` event that carries
  no text is still a failure, and inventing a reason for it would be the fake in the other
  direction. The bar prints the journey's *failed* and nothing after it.
- **`composeStart` is written after the server accepts**, not before the request as §G.1's
  writer table reads (§II.2 is why).
- **Full screen is not driven by the walk**: only the Phylogeny surface offers a full-screen
  control today, and it is not a house surface. `showJourneyBar(surface, full)` is driven under
  `node --test` instead (M5, M6).
