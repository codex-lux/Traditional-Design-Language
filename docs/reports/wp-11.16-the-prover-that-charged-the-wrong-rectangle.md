# WP-11.16's precondition — the prover that charged the wrong rectangle

*14 September 2026. The span half of WP-11.16, shipped as its own commit. The record edit —
tagging `plans/tidewater-georgian-careful.json` — is NOT in this package and is not started.*

## I. Why this is its own commit

`PLAN-OF-ACTION.md`'s WP-11.16 named a precondition and said *"settle it first; it is a
placement change, because the charge is in the prover's objective."* It is settled here, alone,
for WP-11.9's own reason: a package that teaches a layer **and** moves a shipped placement has
done two things and can only be reasoned about as one. This one moves no shipped placement at
all — every plan in this corpus is a single rectangle — but it does move a *multi-element* one,
which is precisely the class of plan the record edit creates.

## II. The defect, and it was worse than the note said

`geometry_cp._score` called `geometry._span_charge` with no `elements=`. The hill-climb has
passed `_span_elements` since WP-11.9; the prover never did. So on a multi-element CP placement:

- `over_capacity` and `charge` were computed with the **whole footprint as one rectangle**,
- while `_disclose_spans` wrote `span_capacity.marks` **per element**,
- and `plan_check` emits one finding per mark while publishing the count beside it.

WP-11.15's audit recorded this as *"3 against 4 on a two-element fixture"* — a disagreement.
Re-derived here on `geometry_cp._multi_element_fixture()`, at `engine="cp"`, it is sharper than
that:

| | before | after |
|---|---|---|
| `over_capacity` (the prover's own count) | **0** | 1 |
| `charge` | **0** | 23.5 |
| `len(marks)` | 1 | 1 |
| `plan_check` span findings | 1 | 1 |

**Zero, not three.** The record was not disagreeing with itself in some arithmetic corner; it
was asserting that **nothing exceeded capacity** over a drawing holding a **37.5 ft clear run
inside the dependency against its own 24.0 ft framing capacity**. A defect reported clear is the
OQ 52 family, and this one sat inside the score `_finish_feasible` ranks its hard-valid
candidates by, so it was not merely mis-reported — it was un-charged.

The mechanism is the same one WP-11.9 removed from `structure.wall_lines` and WP-11.11 removed
from the CP objective, arriving in the third place nobody had looked. Read footprint-wide, the
scan runs over `0..W` and `0..H` — the main block — and credits every room's face as a bearing
line, including the dependency's, so the dependency's own long run is hidden behind bearing
lines that stand in another building.

## III. The fix

One argument, threaded from a list that was already in hand. `_rects_scored` computes
`_els2 = {lv: blocks_for(...)}` ten lines above the call; the span map is that list in the shape
`spans_over_capacity` takes:

```python
_span_els = {lv: [(b["x"], b["y"], b["W"], b["H"]) for b in bl]
             for lv, bl in _els2.items() if len(bl) > 1} or None
```

which is `geometry.py`'s own `_span_elements`, built from `blocks_for` in exactly the same way.
**A level with one element is ABSENT from the map rather than present with a single entry**, so
`spans_over_capacity` takes its `[(0, 0, W, H)]` default and the arithmetic is byte-for-byte what
it was. On a one-rectangle house the whole map is `None`.

`geometry_cp._build`'s span term has been per element since WP-11.11, so **the MODEL did not
move**: `tests/test_cp_elements.py`'s four `CpModel` proto hashes are untouched, which is a
stronger statement than any timing and cost nothing to make.

## IV. What moved

On the fixture, the prover's chosen candidate changed — and in the direction the change is for:

| | before | after |
|---|---|---|
| kept candidate | polish from the heuristic hint | hard-only phase A |
| worst span | 37.5 ft | **28.25 ft** |

`_finish_feasible` scores every hard-valid placement with the heuristic's own scorers and keeps
the best. Once that score can see the dependency's spans, a placement that puts a shorter real
run in the wing wins. That is a placement change on multi-element plans, stated rather than
absorbed.

**Nothing shipped moved.** The corpus is one rectangle everywhere, `_span_els` is `None`, and
`tests/test_appendages.py::test_placing_the_terrace_moved_no_shipped_placement` is unmoved at
`68b102ff6a724e47`.

## V. The guards, and why they are shaped this way

Two, both in `tests/test_span_findings.py`, both mutation-checked with the mutation asserted to
have landed and the file restored byte-identically afterwards.

1. **`test_a_cp_placement_counts_the_spans_it_draws_and_not_the_footprints`** — the value
   property, `over_capacity == len(marks)` on a CP-placed multi-element fixture. It also asserts
   that at least one mark lies **outside the main block**, because a mark wholly inside it is
   counted the same either way: without that clause the test would be *a guard that runs only
   where the bug cannot occur*, which this repository has recorded three times.
2. **`test_the_elements_the_prover_charges_are_the_rooms_own_and_none_on_one_rectangle`** — the
   mechanism, read behaviourally rather than off the source line. A spy on `_span_charge`'s
   `elements=` over the tagged fixture, and over **the same fixture with its `block` tags
   stripped**. The control is what makes it a statement about massing elements rather than about
   one plan: tagged must pass a three-element map, untagged must pass `None`. A source-text
   assertion would have gone blind on the next rewording; both halves of this one bite.

Run six times, the CP property held six times (the fixture proves OPTIMAL in about a second, so
this is not a wall-clock lottery).

## VI. What this does NOT close

The two numbers now agree **by two different definitions of membership**:
`spans_over_capacity` selects each element's rooms geometrically (`EL_TOL = 0.5`) because the
search calls it with rooms that carry no tag at all; `_disclose_spans` selects them by tag. So
the agreement is a property of the placements this corpus produces, not of the code.

Driven, by moving one dependency room 0.6 ft past its element's face — 0.1 ft beyond `EL_TOL`:
`element_of` returns `None`, `len(marks)` goes 1 → **2** with
`element_membership_unresolved` set, and `over_capacity` stays at **1**. The two part company,
and in opposite directions: the tag reader over-reports deliberately, the geometric reader
silently drops the stray room. Raised, with that measurement, as
`oq/the-span-count-and-the-span-marks-read-membership-two-ways`. It fails loudly rather than
quietly, which is why it is a question and not a blocker.
