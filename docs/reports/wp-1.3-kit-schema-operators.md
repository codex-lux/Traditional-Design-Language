*Executed 23 August 2026, overnight autonomous session, in four parts across and after WP-1.1.*

## What was built

**Part 1 — the fourth trade split (OQ 12).** `elements/slots.json` gained `wall_thickness_masonry` / `wall_thickness_frame`, the fourth and last of the four splits OQ 12 called for. Checking the ontology directly (rather than trusting the open question's own prior text — see "what was found" below) showed the other three had already happened, in ontology 0.3.0, predating this ruling and this session entirely, under different names than the ruling specifies (`window_head_wood` not `window_head_carpentry`, `corner_quoin`/`corner_board` not `corner_treatment_masonry`/`corner_treatment_carpentry`, `window_surround_masonry`/`window_surround_wood` as a real split rather than a single id with an added `none` value). `wall_thickness_expression` alone had never been built under any name. Ontology bumped 0.4.0 → 0.5.0 (93 → 95 slots); `build/build.py` rerun, adding the two new slots to all 132 kits as `open`/`empty`.

**Part 1 — `derives_from_module` (OQ 13).** Added to `cornice`, `frieze`, `modillion_dentil` (Envelope / Classical Apparatus) and `crown`, `chair_rail` (Interior), all pointing at `entablature` as the shared module source. No regrouping — every existing id and kit binding stays valid, per the ruling. `build/validate.py` gained a referential-integrity check: a `derives_from_module` value must name a real slot and must not self-reference.

**Part 2 — `rule_append` resolution (OQ 16).** `build/resolve_kit.py`'s `merge_extends` now actually reads `rule_append`: a child delta's value joins onto whatever `rule` the merge step resolved to (inherited, or freshly replaced if the same delta also set a full `rule`) as an additional sentence, recorded in `_rule_append` for provenance. `--slot --verbose` and the group-table view now show which ancestor's delta contributed which clause; JSON output carries the same `_rule_append` field.

**Part 2 — `service_zone_strategy` reconciliation and `docs/inheritance.md` guidance (OQ 17).** A new section in `docs/inheritance.md`, "Two mechanisms for regional conditionality, and when to use which," states the ruling generally: use a variant node's own binding when a region diverges enough to deserve its own identity; use `applies_when.regions` on the parent only when no such variant node exists and a single parameter differs. Applied to the actual case the open question named: `georgian-colonial-american.kit.json`'s `strategy_tidewater` parameter (which duplicated `tidewater-georgian`'s own kit binding) is removed; `strategy_new_england`/`strategy_mid_atlantic`/`strategy_low_country` are untouched, because none of the corresponding variant nodes currently binds this slot.

**Part 3 — date-conditional resolution (OQ 22).** `build/resolve_kit.py` gained `--date YEAR`, `in_period(variant, date)`, and `filter_variants_by_date(variants, date)`. A variant with `applies_when.date_range` is in period if the date falls within its inclusive bounds; an undated variant is always in period. Wired into all three output paths — the group-table summary, the `--slot` detail view, and `--json` (which annotates every variant with `in_period: true/false` rather than filtering, so a downstream consumer decides). Nothing excluded is silently dropped: both text views print what got left out and how many.

## What was found

**Three of four items this open-questions.md already claimed were "Executed in WP-1.3" had not, in fact, been executed — because WP-1.3 had never run.** This was found and corrected as a separate, prior commit before this package's own work began (see `docs/reports/wp-1.1-constraint-rule-language.md`, "what was found," and the correction commit itself). It's recorded again here because it directly shaped how this package started: rather than trusting items 12, 13, 16, 17's prior text, every one of the four pieces below began with checking the corpus directly for what already existed, which is how the pre-existing 0.3.0 splits and the pre-existing `rule_append` usage on `georgian-colonial-american.kit.json` were actually found, rather than assumed away or duplicated.

**`georgian-colonial-american.kit.json`'s own `rule_append` usage on `roof_pitch` is a slightly unusual case: the same delta sets both a full `rule` replacement and a `rule_append`.** Not a bug in the data — MERGE_REPLACE's existing behavior (replace the whole sentence, discarding the ancestor's) runs first, then the new append logic joins onto the freshly-replaced sentence, which is a coherent reading of what the author evidently intended (state the colonial norm in full, then add one more distinguishing clause) — but it meant the first draft of the pinning test, which assumed the resolved rule would start with `english-georgian`'s own rule text, was wrong. Fixed once the actual delta content was read rather than inferred from the CLI's own summary line.

**Every one of the 49 corpus-wide `applies_when.date_range` records is on a `variants` entry; none is on a `parameters` entry**, checked directly before designing `--date`'s behavior. This kept the feature's scope narrow and honest — `eval_parameters` was left untouched, and `docs/open-questions.md`'s resolution for item 22 says explicitly that a date-conditional parameter path is unbuilt and untested, rather than implying broader coverage than what's actually wired in.

**`docs/inheritance.md` had drifted independently of anything this package was asked to fix.** Its slot count (82), its per-group counts, and its Constraints section ("currently prose... pending a rule language," written before WP-1.1 existed) were all stale — not from this session's own work, but simply never updated as the ontology and the constraint rule language moved past what the doc described. Corrected while writing the new regional-conditionality section, since leaving three more inaccuracies sitting a few paragraphs from a section this package was adding would have been the same failure mode the session keeps finding and fixing in other files.

## What was deliberately not done

**The three pre-existing trade-split slots (`window_head_wood`, `corner_quoin`/`corner_board`, `window_surround_masonry`/`window_surround_wood`) were not renamed to match OQ 12's literal wording.** Renaming would mean deprecating three established ids across every kit file, the fault corpus's `slots` references, and anywhere else they're named — real churn for a naming-only difference, and it would violate the corpus's own id-stability rule (`deprecated_in_favour_of`, never rename) for no functional gain, since the existing split already correctly separates structural/masonry from non-structural/carpentry work by the same underlying logic the ruling describes. Left open in `docs/open-questions.md` item 12 as a choice between renaming (a real migration) or amending the ruling's own wording to match what's already built — not decided unilaterally here, because it's a naming-convention call with corpus-wide blast radius, not a functional gap.

**`derives_from_module` was not wired into any enforcement.** The ruling's own wording ("a cross-reference it *can use* to enforce...") describes a latent capability, not an immediate requirement. `build/validate.py` checks the reference resolves to a real slot; nothing yet checks that a chair rail's actual resolved module numerically agrees with the entablature's when both are bound on the same kit. Flagged as a reasonable follow-up in `docs/inheritance.md` rather than built speculatively — the three populated kits in this corpus don't currently bind `chair_rail` and `entablature` together in a way that would exercise the check meaningfully yet.

**No fault was authored against `wall_thickness_masonry`/`wall_thickness_frame`.** Adding two new slots dropped fault-corpus coverage from 93 of 93 to 93 of 95 — noted honestly in `README.md`, `docs/faults.md`, and `docs/open-questions.md` item 25 rather than either hidden or papered over with a rushed low-quality fault entry just to preserve a round number. Authoring a fault to this corpus's own standard (driver, three-tier fix, `test` object, style exceptions) is real work belonging to the fault-corpus layer, not a kit-schema-operators package.

**A `check_kits.py` addition to catch a future recurrence of the `service_zone_strategy` duplication was not built.** `docs/inheritance.md`'s new section says explicitly that nothing enforces the guidance automatically yet. This one instance is fixed; the general case (a variant restating a fact its parent also states via `applies_when.regions` for the same region) would need a corpus-wide sweep across every family with regional variants, which is broader than one open question's scope.
