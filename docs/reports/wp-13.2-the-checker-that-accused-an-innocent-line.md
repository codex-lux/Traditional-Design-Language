# WP-13.2 — the checker that accused an innocent line

*15 September 2026. Raised by WP-13.1's own verification run, deferred in that package's §VIII,
and executed here.*

## I. What happened

WP-13.1 was committed at a stop hook's request with its build unfinished, and the serial
`build/check_all.py --shard 1/1` that followed came back **1 of 53 checks failed**. The failure
was `check_frontend.py`, and this is what it printed:

```
=== check_frontend.py ===========================================
--- lazy tiers
FAIL: three.js is not a separate chunk — `round/three-scene.js` has been imported
      statically somewhere, so every reader now downloads a 3D engine to look at a flat plate
--- router-unit.mjs
router-unit: 63 checks passed
--- search-unit.mjs
search-unit: 13 checks passed

FAIL: 1 of 2 frontend suite(s) failed
```

Two separate defects are visible in those eight lines, and neither is in the code being judged.

## II. It accused a specific line, and the accusation is false

The message names a cause: *`round/three-scene.js` has been imported statically somewhere*. It
is not. Verified in both directions, independently of the JavaScript suite that already pins
them:

- `three` is imported by **exactly one** module in `workbench/app/src` — `round/three-scene.js`.
- `three-scene.js` is reached by **exactly one** import, and it is dynamic:
  `Round.jsx:71` does `import('./three-scene.js')`.

So a reader acting on that message goes hunting for a static import that exists in no file. The
real cause is that the checker was reading `workbench/app/dist/`, which is **gitignored**, was
built **7 Sep 17:11**, and therefore predates `round/three-scene.js` — committed **9 Sep** by
WP-12.4 — by two days. **22 source files are newer than the bundle.** The chunk it was looking
for could not appear in a build made before the code existed.

This is the 4 September entry's own rule arriving with a sharper edge. That entry says *a red
build nobody can act on is worse than no build, because the next real failure arrives inside
it*. This is worse than unactionable: it is **actionable in the wrong direction**, because the
message is specific, confident, and points at a real file that has done nothing.

**The check had two states where it needs three** — `COULD NOT EVALUATE` for an ABSENT `dist/`,
`FAIL` for a present one, and no state at all for *present but built before the code it judges*.

## III. It named the wrong population

`bad` counted the lazy-tier check and the two node suites in one variable, and the summary read
`f"{bad} of {len(SUITES)} frontend suite(s) failed"`. So `FAIL: 1 of 2 frontend suite(s) failed`
printed two lines under `router-unit: 63 checks passed` and `search-unit: 13 checks passed`. A
reader chasing it reads two green files. That is *a refusal with one message for three causes*
(WP-11.4) one layer up: not one message for several causes, but a message naming a population
the failure is not in.

## IV. What was built

Three functions, because three things needed to be drivable:

- **`sources_newer_than(built_at, root=None)`** — the `workbench/app/src` files modified after
  the bundle was written, **named** rather than counted. `root=` is the seam, so a test drives
  it over a tree it built rather than mutating a module global; `modcache` hands every reader
  the same module object, so a mutated `ROOT` outlives the test that set it.
- **`bundle_unjudged_reason(root=None)`** — why this `dist/` cannot be judged, or `""` if it
  can. Three refusals: no `dist/`, no `index.html` to date it by, or sources newer than it.
- **`verdict(tier_bad, suite_bad, tier_unjudged)`** — the check's one verdict as `(code,
  message)`, with the two populations counted apart.

`main()` takes the same `root=` seam and delegates to all three.

**An unjudged bundle returns `COULD_NOT_EVALUATE` and never 0.** One check, one verdict, and the
verdict of a check half of which could not be evaluated is not a pass — `check_all.py` already
maps exit 3 to `N/EV` and excludes it from `failed`, which is the same shape the two CAD
selftests have had since WP-5.1. A real suite failure still outranks an unjudged half.

What the checker prints now, on this tree:

```
--- lazy tiers: COULD NOT EVALUATE (dist/ was built before 22 of the sources it would be
    judged against (first by path: workbench/app/src/Chrome.jsx) — run npm run build)
--- router-unit.mjs
router-unit: 63 checks passed
--- search-unit.mjs
search-unit: 13 checks passed

COULD NOT EVALUATE: 2 frontend suites are green and the lazy-tier check was not judged — …
```

Exit **3**.

## V. The heuristic, and the direction it is allowed to be wrong in

An mtime comparison is a heuristic and the module says so. It errs toward **UNJUDGED** in both
directions that can occur: a checkout that rewrites a source's mtime over a current bundle reads
stale and is reported so, and a bundle built from a different tree with older mtimes reads
current. **It never errs toward a PASS**, which is the only direction that would matter — a
freshly built `dist/` is newer than every source by construction, so a genuine static import
still reaches the `FAIL` branch. There is a test asserting exactly that property.

WP-13.1's §VIII proposed comparing against *the newest in `dist/assets`*; this compares against
`dist/index.html`, which Vite rewrites on every build and which is one file rather than a scan.
The difference is not material and is recorded because the report said the other thing.

## VI. Four defects in this package's own work, none found by reading it

1. **`sources_newer_than` was walked twice** — once in the branch condition and once in its
   body. Two readings of a mutable tree under one name, which is this repository's own *one
   quantity, two derivations* inside four lines of its own fix. Read once now.
2. **`newer[0]` was labelled "oldest offender"**, and the list is sorted **by path**. A small
   false label on a diagnostic is how a reader is sent to the wrong file — the defect this
   package exists to remove, committed in the sentence removing it. It says *first by path* now.
3. **An unsorted `os.walk`, caught by `test_determinism.py` from inside the running build.**
   `sources_newer_than` walked the tree and sorted the filenames *on the next line*, which is
   deterministic in the result and invisible to a line-based guard —
   `test_corpus_globs_are_sorted` forbids an unsorted directory read anywhere in the toolchain
   and flagged both new files. The fix is `sorted(os.walk(...))`, which is the stronger claim
   anyway: it fixes the **traversal** order too, not only the order within each directory.
   Worth knowing how it arrived: that test reads sources **at run time** and sits at the end of
   a 45-minute suite, so a file edited while the build is in flight is judged by it. The edit
   here was deliberate and the catch is the system working — but it is the reason a mid-run
   edit is never free, even when nothing collected imports the file.
4. **The `root=` seam was wired in one place and not its neighbour.** `sources_newer_than`
   walked the passed `root` and computed `os.path.relpath(path, ROOT)` against the module
   global, so a driven tree came back as `../../../tmp/tmpwr0q60kv/...`. Invisible in
   production, where `root` *is* `ROOT`. **Caught by the function's own first test run**, not by
   reading it.

## VII. What the full build said

`build/check_all.py --shard 1/1`, serial, one checkout, 45 minutes of pytest:
**2 of 53 checks failed, 2,252 passed, 25 skipped**, three unjudged as always (both CAD
selftests and — on this container — nothing else, `workbench/server/tests` having fastapi here).

Both failures are accounted for and neither is WP-13.1's:

- **`check_frontend.py`** — the defect this package removes. The run had already passed that
  check's section before the fix was written, so it is the OLD code's verdict.
- **`tests/test_determinism.py::test_corpus_globs_are_sorted`** — **this package's own**, the
  unsorted `os.walk` above, introduced mid-run and caught by an existing guard.
- **`tests/test_shape_pins.py::test_no_room_is_drawn_outside_its_own_band_when_the_pins_hold`**
  — the documented intermittent of
  `oq/a-held-shape-pin-is-not-held-on-the-hard-only-path`. Attributed rather than called a
  flake, by the method CLAUDE.md prescribes: six runs alternating a `git archive` of
  **`840c7f1`** — the base commit, which carries neither WP-13.1 nor WP-13.2 — against the
  working tree, to control for machine load.

  **6 of 6 failed, 3 on each tree**, which is 15 Sep's rate and a third data point for
  CLAUDE.md's standing rule that the rate is a property of the machine and the day (2 in 8 on
  8 Sep, 8 in 8 on 9 Sep). **And this run says something the earlier ones did not: all six
  convictions are IDENTICAL** — `('chamber3', 1.4, 1.35)`, the same room drawn at the same
  ratio against the same ceiling, with `downgraded_shape_pins` empty. The existing entry
  establishes that the two trees agree on the RATE; this establishes that they agree on the
  VERDICT, which is the stronger claim and settles the attribution completely. The solver
  status was not captured (`pytest -q` does not print it), so which path produced it is not
  measured here; convicting `chamber3` alone is the signature CLAUDE.md attributes to the
  polish path, and that is consistency rather than a measurement.

Everything else in the corpus was green, which is what WP-13.1's commit was waiting on.

## VIII. Verification

The checker had **nine behaviours and no test file at all** — the shape CLAUDE.md records for
`build/family_source_hazard.py`. `tests/test_check_frontend.py` is 21 tests in five classes.

**Thirteen mutations, thirteen red**, each asserting it LANDED before the colour was believed
and each restored byte-for-byte in a `finally`. The sweep mattered:

- **Three were BLIND on the first run**, and all three were in `main()`'s inline wiring —
  deleting the staleness test, inverting it, and loosening `>` to `>=` all left the suite green,
  because the parts were driven and the join was not. `bundle_unjudged_reason` exists because of
  that sweep.
- **One more was blind after that**: `main()` could stop calling the reader altogether and every
  part-test stayed green. That is **WP-11.14's finding in a new place** — each half asserted, the
  wiring asserted by nothing. `main()` got the `root=` seam so the join could be driven on any
  machine rather than on whichever state this checkout's gitignored `dist/` happens to be in.
- **The `>` / `>=` mutation needed an EQUALITY fixture.** Every other fixture leaves a whole
  second between the two mtimes, and at a one-second gap `>` and `>=` return the same answer.
  This is WP-10.1's `round(542/22/10) == round(542/36/10)` lesson and WP-11.15's *a fixture where
  both branches return the same number guards neither*, met in a comparison operator. Under
  `>=`, a source written in the same instant as the bundle reads stale — on a fast machine that
  is every build, and the check would go **permanently unjudged**, which is the fake-unjudged
  direction and exactly as dishonest as the false FAIL removed here.
- **One mutation did not land twice** — `base = root or ROOT` occurs in three functions, and an
  anchored re-cut was mis-spliced into a `SyntaxError`. Neither run was read as evidence;
  `landed: 0` is not evidence of anything. Re-anchored on a unique preceding comment, it is red.

Every refusal is DRIVEN, because none of these states is reachable from a correct checkout:
each staleness fixture builds its own tree in a tmpdir and passes it as `root=`, and nothing in
the file reads the repository's own `dist/`, which is a property of whoever last ran
`npm run build` rather than of the corpus.

Three tests assert **premises** — that the driven tree really is stale, that a judgeable bundle
that fails really FAILS rather than going unjudged (without which returning `COULD NOT EVALUATE`
unconditionally would satisfy the two refusal tests), and that `three` is really a dependency in
`package.json` (without which the two source guards pass on an app that cannot draw the Round).

## IX. What was deliberately not done

- **`dist/` was not rebuilt.** `npm install` would have put `node_modules` on the tree while
  `node --test workbench/app` was still pending in the running build, and CLAUDE.md records that
  that suite runs with **no npm install** — a package import there is a green local run and a red
  CI one. Rebuilding would have masked exactly that. The bundle half therefore stays **unjudged
  here and judged in CI**, which builds before it checks; that is what the third state is for,
  and it is the honest resting position rather than a gap.
- **The lazy-tier thresholds were not touched** — 700 KB entry ceiling, two tier chunks, the
  `three-scene-` chunk. This package changed *when* the check may speak, never *what it says*.
- **`len(CHECKS)` did not move**, and no new checker was added. The arithmetic identity CLAUDE.md
  records (`TOTAL_CHECKS - 3 == len(CHECKS)`) is stated for a tree with the CAD libraries and
  fastapi absent; on a checkout whose `dist/` is stale there is now a **fourth** unjudged check,
  and that is disclosed rather than engineered away. It is unaffected in CI.
- **`check_costs.json` was not updated** for the new test file. The table is a HINT: `assign()`
  is total over `units()` whatever the table says, and a missing entry costs balance and nothing
  else.

## X. Verdict

The one FAIL standing between WP-13.1 and a clean build was an instrument reporting a false
cause about a bundle it could not legitimately judge. It is three states now, it names the file
that made it unjudgeable, it counts its two populations apart, and it has the test file it never
had. The source-level guarantee the lazy-tier check exists to protect — `three` behind one
dynamic import — is asserted in Python as well as JavaScript, so a machine with no node and no
bundle still learns whether the invariant holds.
