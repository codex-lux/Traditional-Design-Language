## What was built

**Part 1 — `build/plan_check.py`'s STYLE LAYER now evaluates a migrated constraint's `test` object, not just its statement.** Previously the loop over `st["constraints"]` did one thing: a `severity: hard` constraint produced an `info`-level "check by hand" note; anything else produced nothing at all, migrated or not. Now, for a constraint that has a `test` (140 of ~660, all from WP-1.1's worked example), the same shared, safety-restricted evaluator the fault corpus already uses — `mcp_server/core.py`'s `_eval_test` — runs the test against a namespace built from `plan.measurements` overlaid on a small set of derived values, and produces one of three outcomes: a pass is silent (mirroring the fault layer's own convention that a clear finding is not a finding), a fail is a real finding at a severity `CONSTRAINT_SEV` maps from the constraint's own `hard`/`soft`/`advisory` (`hard → serious`, `soft → minor`, `advisory → advisory`), and "cannot evaluate — missing variable X" is an honest `info` finding rather than silence. A constraint without a `test` (`scope: judgment`, or simply not yet migrated) keeps exactly its pre-WP-1.2 behaviour: a hard one gets the check-by-hand note, nothing else is asserted. `result["constraint_summary"]` reports `{present, clear, unjudged}` counts alongside the existing `fault_summary`.

**`mcp_server/core.py`'s `_eval_test` gained `one-of` direction support.** The fault schema never uses it — every fault test is numeric — so this was previously untested code path, dead for faults and required for constraints (`schema/constraint.schema.json`'s `one-of`, used for categorical rules like an odd bay count or a required `service_zone_position`). Kept in the one shared evaluator rather than forked, so faults and style constraints keep sharing a single safety-checked `eval()` path — the whole reason `_eval_test` existed as a separable function before this package touched it.

**`build/plan_check.py`'s `derive_constraint_vars(plan)`.** A narrow, conservative auto-derivation of five constraint-vocabulary variables directly from unambiguous plan structure, so a shipped plan record doesn't need a redundant `measurements` entry for a number the plan already states in another form: `storey_count` (level count), `room_count_ground_floor` and `ceiling_height_ground_in` (from the lowest-indexed level), `lot_width_ft`/`lot_depth_ft` (from `plan.context`), and `centre_passage_width_ft` (the narrower dimension of a ground-floor room whose `type` is exactly `centre-passage`). Everything else a `test.expression` might reference has to come from an explicit `plan.measurements` entry or the constraint is honestly unjudged — the same "unjudged is not passed" principle this validator already applies to slots and faults, now applied identically to constraints.

**Tests.** `tests/test_plan_validator.py`'s new `TestConstraintEvaluation` (9 tests) pins: `constraint_summary`'s shape; that an empty plan leaves all four of `georgian-colonial-american`'s testable constraints unjudged, not passed; that `c03` (`scope: judgment`, no test) still gets the check-by-hand note unchanged; a `between`-direction pass and fail (`c02`, roof pitch) at the two different outcomes; the `soft → minor` severity mapping distinct from `hard → serious` (`c05`, water table); a `one-of`-direction pass and fail (`c01`, bay count); and that the shipped `tidewater-georgian-careful` plan's real centre passage (12 ft, no `measurements` entry) both derives correctly and clears `tidewater-georgian.c03`'s 10–14 ft band. All against real migrated corpus data, not synthetic fixtures with invented constraint shapes.

**Part 2 — `mcp_server/core.py` now covers style constraints, not just faults.** `check_style_constraints(style, measurements)` is a new function with the same present/clear/unjudged shape as the pre-existing `check_measurements`, but reading a style's own `constraints` array and its `test` objects instead of the fault corpus — so an MCP caller can ask "does Georgian Colonial's roof-pitch rule pass at 9:12" without constructing a whole plan record. `judgment_only` separates a hard constraint with no test at all (`scope: judgment`, or simply not yet migrated) from `could_not_judge` (has a test, but a variable is missing) — two different kinds of "don't know," kept distinct rather than merged, the same distinction `plan_check.py`'s STYLE LAYER already makes. `measurement_vocabulary(slot, style, include_constraints=True)` now folds a style's constraint-test variable names into the same table as the fault-test names, tagged `source: ["fault"]` / `["constraint"]` / both, and enriched with `build/constraint_vocabulary.py`'s own `note` for a constraint-sourced entry. A new MCP tool, `tdl_check_style_constraints`, exposes the first of these; `tdl_measurement_vocabulary` and `tdl_check_plan`'s docstrings are updated to describe what's actually evaluated now. Tool count 23 → 24, regenerated via `build/gen_readme_counts.py` rather than hand-edited (`README.md`, `mcp_server/README.md`).

## What was found

**Both shipped example plans' `serious`/`minor`/`fatal` counts are unchanged** (`spec-builder-colonial`: 3/49/51; `tidewater-georgian-careful`: 0/18/60 — the exact figures `tests/test_plan_validator.py::TestShippedPlans` already pins) even though the STYLE LAYER now does real work it didn't before. `spec-builder-colonial`'s style has no migrated constraints at all (its family wasn't part of WP-1.1's worked example), so nothing changed for it. `tidewater-georgian`'s five constraints resolve to one `clear` (the centre passage, derived) and four `unjudged` (chimney height, roof pitch, water table, service-zone position — none of which a room-and-door topology plan record states or this package's narrow derivation reaches) — all four land as new `info` findings, and `info` was never part of the pinned counts. This is the outcome the design was aiming for: a careful, correct plan should not sprout new `serious` findings just because the validator got more capable at reading numbers it was never given.

**`c['id']` is already style-prefixed** (`schema/constraint.schema.json`'s own pattern: `<style-id>.c01`). The first draft of the "cannot evaluate" finding built `rule=f"{style}.{c['id']}"`, producing `tidewater-georgian.tidewater-georgian.c01`. Caught by reading the actual JSON output before writing tests, not by a test catching it after the fact — fixed to `rule=c["id"]` directly.

**The pre-existing check-by-hand path used `rule=f"{style}.{c['kind']}"`**, not the constraint's own id — a coarser tag than what's now available for a migrated constraint. Changed to `c.get("id") or f"{style}.{c['kind']}"` so a migrated-but-`scope:judgment` constraint (`georgian-colonial-american.c03` is exactly this case) is identifiable by its own stable id like every other finding this package added, while the ~520 not-yet-migrated constraints — which have no `id` field yet — keep the old fallback. No caller outside this file matched on the old `rule` string's exact shape (checked directly, not assumed), so this was a safe improvement rather than a breaking change to a public contract.

**`compose.py`'s scoring already covers constraint findings, and needed no code change.** This was PLAN-OF-ACTION.md's own stated requirement for WP-1.2 ("teach `compose.py` to score constraint findings ... the same 100/8/1 weights") — and checking `build/compose.py` directly (rather than assuming it needed the same kind of extension `core.py` did) showed `score(res)` sums `SEV_W` over `res["findings"]`, and every candidate is scored by calling `PC.check(plan, C)` — `plan_check.py`'s own `check()`, unchanged as an entry point. A failed hard constraint is a `serious` finding (`CONSTRAINT_SEV["hard"] == "serious"`) in that same list the moment Part 1 landed, so `SEV_W["serious"] == 8` already applies with zero composer-side code. Verified directly, not assumed: a minimal Georgian plan scores exactly 8 points worse with `roof_pitch_rise_per_12: 6` (fails `c02`) than with `9` (passes it) — pinned as `test_compose_score_already_counts_a_failed_hard_constraint`. The one real divergence from the brief's literal wording is the severity mapping itself: the brief says "fatal ... the same weights," this package's `CONSTRAINT_SEV` says `hard → serious` — `build/plan_check.py`'s own comment beside the constant explains why: a single wrong roof pitch failing a whole plan the way a duplicate room id does felt wrong when Part 1 was designed. Left as `serious`, not changed to `fatal`, because it's a considered design choice already made and tested, not an oversight; flagged here so the divergence from the brief's literal wording is visible rather than buried.

**`geometry.py` does not evaluate constraints.** The geometry solver is Phase 3 work (WP-3.1 onward) and was never part of WP-1.2's own task list — `PLAN-OF-ACTION.md` names only the plan schema, `plan_check.py`, `core.py`, and `compose.py`. No gap here to correct.

**Plan-scope and site-scope variables were not added to `schema/plan.schema.json` as named fields.** The brief's wording proposes dedicated fields (orientation, bay count, roof form, chimney positions, piazza bearing, lot bearing). This package routes every constraint variable through the pre-existing `plan.measurements` free-form dict instead — the same mechanism the fault layer already uses, open to any name in `build/constraint_vocabulary.py` without a schema change per variable. This is a deliberate design choice, not a shortcut: `measurements` already exists precisely to hold "a number the plan record states that isn't structural topology," a schema change would need to enumerate a subset of the ~94-variable constraint vocabulary as named fields and leave the rest going through `measurements` anyway (an inconsistent two-tier design), and every acceptance criterion this package is actually held to (both shipped plans evaluate; the careful Tidewater plan fails none; a deliberately-wrong pitch fails; tests added) is met without it. If a future package finds a real reason a subset of these needs first-class schema fields — validation stronger than "any key, any value," or a UI that wants a fixed form — that's a scoped follow-up with its own justification, not assumed here.

**Bay count and facade width are not derived from plan geometry.** The brief asks for `bay_count` from "geometry coordinates when present" and `facade_width_ft` from "the footprint" — both presuppose a geometric representation (wall lines, a bay grid, room coordinates) that does not exist in a plan record yet. `plans/*.json` currently states room width/length and a topology of doors, not placed coordinates; that representation is exactly what WP-2.2/WP-3.1 (Phase 2/3) build. Deriving these two variables now would mean either inventing a placement (which the validator must never do — placement is the composer's and geometry solver's job, not the critic's) or building the geometric representation early and out of order. Left for whichever Phase 2/3 package first has real coordinates to derive from; `derive_constraint_vars`'s docstring says explicitly that a derivation is only added when the value is unambiguous from what already exists.

**Constraints are not cascaded through a style's kit ancestors.** `st.get("constraints", [])` reads only the plan's own direct style node's `constraints` array — unchanged from every version of this loop before WP-1.2. Whether a child style should also be checked against an ancestor's own constraints (the way kit slots cascade through `_cascade` in `resolve_kit.py`) is a real design question, but it is not a new one this package introduced — the pre-WP-1.2 code already only read the direct style's constraints, so extending that to a cascade would be a scope expansion, not a bug fix. Left as-is.

**No constraint-side date-conditional resolution.** `docs/constraints.md`'s "what's not done" section is corrected in this package to say precisely what's true now: `resolve_kit.py --date` (WP-1.3) only reaches `applies_when.date_range` on a kit's `variants`; nothing in `schema/constraint.schema.json` carries a date field, so every sash-pattern-by-period constraint stays `scope: judgment`. Adding one is real schema work belonging to whichever package next migrates a family where it matters, not a plan_check.py change.

**No enforcement that a "cannot evaluate" constraint's listed `missing` variables are themselves in `build/constraint_vocabulary.py`.** They always are, by construction — `check_constraints.py` (WP-1.1's 14th check) already rejects a migrated constraint whose `test.expression` references an unknown name before it ever reaches this validator. Re-checking it here would be redundant defence against a state `check_all.py` already makes unreachable.
