# WP-14.7 — the walk navigates by address

*24 September 2026. Branch `wp-14.7`. Scope: `workbench/app/e2e/walk.mjs` and this report,
nothing else. Every figure below was measured on this tree, in this worktree, with
`HEAVY_CALLS_PER_HOUR=100000 WALK_PORT=8201 bash workbench/scripts/walk.sh` against a freshly
built `workbench/app/dist/`; nothing is quoted from another report. Cite this report by
filename.*

## What it is for

Phase 14 rebuilds the workbench's navigation: later packages rename the rail's items, move the
Kit into a Style Dossier, and add dialogs of their own. The browser walk reached eleven of its
surfaces by **clicking the rail by its label** — fourteen clicks spelling `The Kit`, `Style
Record`, `Drawing Set` and the rest — and found the command palette as **the page's only
`[role="dialog"]`**. Both happen to hold on today's app (it never has two dialogs open at once)
and neither is what any of those checks is about. Left as they were, every Phase 14 package touching the rail or adding a dialog would have
had to re-cut walk lines belonging to surfaces it never touched, and several packages would have
fought over the same lines.

This package goes first and removes both dependences **without changing what any check means**.

## I. What was built

**`visit(hash)`.** Sets `location.hash` to the address exactly as `nav.go(surface)` writes it
for a surface with no selection (`state/nav.js::write` does `location.hash = formatHash(...)`,
and `router.js::SURFACE_PATHS` gives each surface's path), waits for the `hashchange` the app
listens to and one frame, then waits for `main`. It **refuses an address the router does not
write**: `parseHash` sends anything it cannot read to the Overview, so a mistyped `'#/kti'`
would have put a whole block on the wrong surface with nothing saying so. The guard holds the
address to `formatHash(parseHash(h)) === h` and to a key of `SURFACE_PATHS`, and it prints a
FAIL only when it fires, so it adds no line to a passing tally. The router is imported from
`src/router.js`, which is import-safe under node (its one import is `citations.js`, which imports
nothing) — the same way the walk already imports `src/state/layout.js`.

it byte-identical:

The one at old line 1494 is the case where *how* the walk leaves matters, because the check after
it is *"filters survive leaving and coming back"* through `page.goBack()`. The rail click left by
`nav.go`, which assigns `location.hash` and so pushes a history entry; `visit` assigns
`location.hash` too. The history the `goBack` walks is the same shape either way.

**The reachability loop.** Removing the fourteen clicks removes the only thing that ever clicked
the rail, so reachability from the rail is now asserted once, by itself: every button rendered
under `nav[aria-label="surfaces"]` (less the fold control, which carries `aria-expanded`) is
clicked once in rendered order, and each must

- move the address (an item already current is first moved off, onto another surface the router
  knows, because clicking the item you are on proves nothing — a dead `onClick` there passes);
- land on an address the router writes (`formatHash(parseHash(after)) === after`);
- be the **one** item the rail then marks `aria-current="page"`;
- land somewhere no earlier item landed.

Each item is clicked while the previous item's surface is mounted, so the rail is still clicked
over eleven of the twelve surfaces — the other thing the fourteen clicks tested in passing, that no
surface draws over the rail — though now with no plan loaded, where most of those clicks had one.

**Which surface is "its own" is read off the item, not off a list in the walk.** The brief
suggested importing `Chrome.jsx`'s `surfaces()` if it were import-safe under node; it is not (it
is JSX over React, and its imports pull in `Eyebrow.jsx` and `Icon.jsx`), and a table of labels
typed into the walk is exactly the dependence this package removes. `LeftRail` binds
`aria-current` to `current === it.id` with the same `it.id` its `onClick` hands to `onGo`, and
`current` is the surface `nav` parsed out of the hash — so *this item and no other is current*
says the hash parses to this item's surface. The distinct-address half does not read
`aria-current` at all, so an item whose id lands on another item's surface fails whatever the
marking says. Before the loop, one premise check: the rail offers something to reach
(`labels.length > 0`), because an empty selection makes every assertion after it vacuous.

**It sits after the Overview block, not inside the rail block the brief pointed at**, and the
reason is that one placement would have changed what an existing check means: *"a cold load lands
on the Overview"* reads `page.url()`, and inside the rail block it would have read an address the
loop had just set rather than the cold load. After the Overview block nothing is lost. The loop
ends by visiting the Overview, which is where the old walk stood when it went to the bench.
**Nothing heavy mounts**: no plan is loaded at that point, so the bench fetches the plan schema
and the Drawing Set fetches nothing (`DrawingSet.jsx` returns early on `!plan`), which was read
before the placement was chosen, because a solve started there would have run on the one core
the bench's own 150 s solve wait later depends on.

**The palette, by its name.** `CommandPalette.jsx` puts `aria-label="Search the corpus"` on its
dialog element, and the walk now finds it as `getByRole('dialog', { name: 'Search the corpus',
exact: true })` (the masthead button carries the same words, and the role keeps it out). Its
results are read inside it — `[role="option"]` is also the style combobox's list, which the
walk's own `pickStyle` clicks on the bench. `waitForSelector` became `locator.waitFor`: both
default to `visible` and both throw on timeout, so the failure behaviour is the same.

**The keys card, by its name too — an extension of the brief, stated.** The brief named only the
palette, but the keys card at old line 1569 was located by the same `[role="dialog"]` and read
with `innerText()`, which throws on a strict-mode violation the moment a second dialog is open.
It is `getByRole('dialog', { name: 'Keyboard shortcuts and addressing', exact: true })` now, the
name `ShortcutCard.jsx` puts on its dialog. One line, the same class, and the dialogs the next
package adds would otherwise have reached it.

**`shot(name, widths)`.** Defaults to the width the walk opens at (1680) and writes `<name>.png`
there, which is the file every call wrote before; `shot(name, [1280, 1440, 1680])` also writes
`<name>-1280.png` and `<name>-1440.png`, resizing for each and putting the window back. The
launch width keeps its unsuffixed name on purpose: widening a call later never renames the file
an earlier review was held against. All 26 existing `page.screenshot` calls go through it.

**The lines `engineClaim.test.mjs` reads are byte-identical.** Its test *"the walk states its
contract from the API status"* holds `walk.mjs` to five regexes. Every line matching any of them
— and the whole block from forty lines above `mayClaimProof` to ten below it — was compared
between the original and the new file: identical, line for line (`mayClaimProof …` 1/1,
`^OPTIMAL\b` 1/1, `solver.objective` 1/1, `data-engine-claim` 4/4, the two retired phrases 0/0).

## III. The mutation: can the loop fail?

`src/Chrome.jsx`'s `LeftRail` was edited so the Kit's item hands `onGo` an id no surface has —
`onClick={() => onGo(it.id === 'kit' ? 'wp-14-7-mutation-no-such-surface' : it.id)}` — and the
app rebuilt. **The mutation was asserted to have landed before the walk was believed**: the string
is in `src/Chrome.jsx` once and in the built bundle (`dist/assets/index-*.js`). The walk then
reported, of the loop:

    FAIL the rail item "The Kit" reaches its own surface (#/) -- the rail marks "Overview"
         current; "Overview" already reached #/

and nothing else: **227 ok, 1 FAIL, exit 1** — 228 less the Kit's item. Every block after the
loop still ran to the end, including the Kit's own block, which is reached by `#/kit` now and
does not care what the rail's button does.

`nav.go` with an unknown surface falls through `formatHash` to the Overview's `#/`, so both
halves caught it independently: the marking (the Overview item, not the Kit, is current) and the
distinct address (the Overview item had already reached `#/`).

**The same run exercised `shot`'s other branch**, which no call in the walk takes yet: a
temporary `shot('probe-end', [1280, 1440, 1680])` before `browser.close()` wrote
`probe-end-1280.png` at 1280 × 1000, `probe-end-1440.png` at 1440 × 1000 and `probe-end.png` at
1680 × 1000, and the viewport read `{"width":1680,"height":1000}` afterwards.

**Restored and proved restored.** `git checkout -- workbench/app/src/Chrome.jsx` returns the file
to its pre-mutation SHA-256 (`8e7f43c2…`), `walk.mjs` was copied back from the saved final and
matches it (`1ee601b4…`, no `probe-end` left in it), the probe screenshots were deleted, and the
rebuilt `dist/` hashes to exactly what it hashed to before the mutation (`6aad1e7a…` over every
file), which is the build the 228 in §II were measured on.

## IV. What was found

**The fourteen clicks were a reachability test nobody had meant to write, and it failed by
dying.** The ORIGINAL walk was run against the same mutated build (copied beside `walk.mjs` as a
throwaway, on its own server, and deleted afterwards). It passed 76 checks, reached the Kit block,
clicked `The Kit` — which took it to the Overview — and waited twenty seconds for
`text=thin kit is correct`, which the Overview does not draw (the probe file was the original
`walk.mjs` byte for byte, so its line 987 is the original's line 987):

    page.waitForSelector: Timeout 20000ms exceeded.
      - waiting for locator('text=thin kit is correct') to be visible
        at …/e2e/walk-orig-probe.mjs:987:12  { name: 'TimeoutError' }

An uncaught `TimeoutError` at the top level, **139 of 215 checks never run**, and a message that
sends its reader to the Kit's cascade note rather than to the rail. The defect was caught, in the
sense that the process exited non-zero; it was not *named*, and the 139 checks after it were
neither passed nor failed nor listed as unjudged -- they simply did not happen. That is WP-13.9's finding about the sheet wait (a top-level throw taking every later
check with it) in a second place. The loop names the item, and the Kit's own checks still run.

**The palette was never the app's only dialog.** The keys card is a second one, located by the
same selector sixty-three lines further on; the two are never open at once, which is the only
reason neither read ever met a strict-mode violation. Phase 14's definition popovers would have
been the third.

**A walk literal can send a block to the wrong surface in silence.** `router.parseHash` resolves an
unreadable address to the Overview by design (*"an unreadable hash resolves to the default surface
rather than a blank screen"*), which is right for a reader and wrong for an instrument: a typo in
a `visit` literal would have run the Kit block against the Overview and reported the Kit's checks
as failures of the Kit. `visit` refuses such an address by name.

## V. What was deliberately not done

- **The rail's label checks were not touched** — *"left rail shows live style count"*, *"all
  twelve surfaces in the rail"*, *"no work-package numerals in the rail"*. Their subject IS the
  labels, so reading the labels is not a dependence to remove; the package that rewrites the rail
  from its navigation model owns them.
- **The palette's result check still reads the words `Fault Corpus`** (*"a newcomer word finds the
  fault corpus"*) — that is the palette's entry label, not a rail click, and it belongs to the
  package that rebuilds the palette's entries.
- **The loop asserts distinct addresses, not distinct surfaces.** Today they coincide (twelve
  items, twelve surfaces). A rail that offers the style index and the style in hand side by side
  will reach one surface at two addresses, and a distinct-surface rule would have convicted it.
- **No assertion that every surface in `SURFACE_PATHS` has a rail item.** It holds today, and a
  package adding a route before the rail item that reaches it would have gone red for a reason that
  is not a defect.
- **No `Chrome.jsx` import by transpiling it in the walk**, and no regex over its source for the
  `id`/`label` pairs: the first drags React into a node script, the second is a selector-shaped
  guard of the kind that goes quietly blind the day the rail is generated from somewhere else.
- **No other file was edited.** `Chrome.jsx` was edited for the mutation only and restored from
  git; the restore is recorded in §III.
