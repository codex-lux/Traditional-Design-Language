# WP-14.25: the plan type starts the brief

*25 September 2026. Phase 14, tranche 2. The contract is `docs/prd/phase-14-tranche-2.md` §C.5
(whose server half WP-14.19 built), §0.3 default 4, §F and §G. Cite this report by filename:
Phase 14's numbers are this line's, and a number does not disambiguate a package in this
repository.*

## What it is for

Lucas ruled on 25 Sep 2026 that a brief may name a parti, and that the composer guarantees the
named diagram a place among the candidates. A parti that is not native to the style is borrowed,
and it says so. WP-14.19 built the server half: the brief schema at 0.2.0, `compose.nativity`,
the guarantee, the refusal by name, and `/api/partis` listing lineage partis beside native ones.

**This package is the page half.** A reader who has just read a plan type on a style's dossier
can now start the brief that names it. The brief carries the name through to the composer, and
the candidate that comes back says it was named. Along the way, the three app readers that
WP-14.19's report said read every listed parti as native now read the nativity the server
states.

## I. What was built

- **The dossier's Plan types section.** Each parti row carries a link, *start a brief from this
  plan type*, to `formatHash('brief', {style, parti})`, which is `#/brief?style=…&parti=…`. Beside
  it is the row's served nativity, worded by its own record (`parti-native` or `parti-lineage`).
  - The link's word is a new glossary record, `start-a-brief-from-a-plan-type`. It is editorial,
    in family `house`, and its basis quotes the brief schema's own `parti` description.
  - A `Term` is a button and cannot sit inside an anchor. So the link prints the record's own
    `term` through `termView`, and its description comes from `useTermDescription`, the way the
    journey bar's steps do it.
  - Across the corpus the section lists **422 rows over 132 styles, 160 native and 262 lineage**,
    and every one of them is now a way into a brief.
- **Brief Intake.** A parti select lists the style's own plan types, grouped by the nativity the
  server states. Each group is labelled by its record's `term`: an `<optgroup>` label is a string,
  so it holds the word and not a `Term`.
  - The chosen parti's nativity sits beside the select as a `Term`.
  - Borrowed diagrams come only behind *include borrowed*. That choice is a URL filter
    (`borrowed`, `widens: true`), and it asks the same route with `include_borrowed=true`. From
    that second list only the rows the server calls `borrowed` are taken, so a native row is never
    offered twice or under the wrong word.
  - `?parti=` seeds the brief, as `?style=` does. A parti the brief names that no group holds is
    **shown as itself** (`data-off-list`) rather than dropped. This covers a borrowed diagram
    whose list the reader has not asked for, or an id nobody holds.
  - The server's refusal is shown in its own words: `e.body.detail.detail`, the composer's
    sentence.
- **`journey/briefForm.js`** holds the three decisions the form had no test for:
  - `composeRequest(brief)` is the brief the form POSTS. It drops blanks and keeps `parti`. A
    count that is not one or more is left to the client's default. This was an inline expression
    in the JSX with no test.
  - `partiOptions(own, borrowed, current)` builds the groups and the off-list parti.
  - `nativityOfParti(options, id)` returns the nativity of the parti in hand.
- **The Candidate Set.**
  - `isNative` reads the served nativity. A candidate's own `nativity` comes first, then the
    style's list as an id → nativity **Map**. Last is the old prose test, for a result composed
    before WP-14.19.
  - A candidate carrying `named_by_brief` shows the `named-by-the-brief` record as its flag.
  - A `named_parti` whose `returned` is false prints its `why`. That is the composer's own
    sentence: the lot dropped it, or it was never composed.
- **The journey bar's composing words** read *k of N* from the stream's own `total`.
  - `k` is the number of diagrams the stream has heard from. That counts both `candidate` events
    and the lot's `dropped` stage events.
  - Where no event carries a total, the words say *k scored* and invent no denominator.
  - `composeProgress()` is exported and driven directly.
- **The feasibility panel's loading state is not a `JudgmentMark` any more.** A request in flight
  is not a verdict on anything. It is `aria-busy` and draws nothing, because the record that would
  word a loading mark is not this package's to author.
- **`glossary/section-plans.json` is corrected.** Its definition and its page-head *read* line
  said the section lists *"the plan diagrams native to"* the style. Since WP-14.19 it lists native
  and lineage diagrams, so the page's own head said something false about the list beneath it.
  The words now say *drawn for it or its line*, *each marked native or lineage*, and that each
  diagram can start its brief. The basis quotes `core.list_partis`, `compose.nativity` and the
  schema.

## II. What was found

1. **The three readers read a lineage parti as native, in three different ways.**
   - The feasibility panel took `/api/partis`'s whole list as "native". Its count called
     `side-hall-townhouse` native to `tidewater-georgian`, and the server calls it lineage.
   - The panel's *no native parti* advisory named three styles in its own detail text:
     `egyptian-revival`, `new-urbanist-traditional` and `tuscan-vernacular`. Since WP-14.19 all
     three list lineage partis, so the advisory could not fire for any of the styles it named.
   - The Candidate Set built a `Set` of listed ids and read *on the list* as *native*.

   Measured now: **3 buildable styles have no native parti and 0 have neither native nor
   lineage**. So the panel's *"has no native and no lineage parti"* branch is a fallback the
   corpus cannot reach. It is kept, because a style with no plan types at all is a state the
   server can serve.
2. **The copy ratchet's baseline carried the advisory's hand-typed count.** Its row
   `["surfaces/BriefIntake.jsx", "132 styles"]` came out when the advisory's detail text did, and
   the baseline only ever shrinks.
3. **The count line on the Candidate Set reads "returned 2 of 1 asked for" when the named parti
   is appended.** This was measured in a direct compose probe, not on the walk: `tidewater-georgian`,
   `side-hall-townhouse` named, one candidate asked, a 3,200 sf target, no `must_have` rooms and
   `revise` off. There the composer's own first choice was a different diagram, so the named one
   was appended as candidate 2. On the walk's brief, which carries the example draft's library and
   breakfast room, the same diagram came back ranked first and the strip read "returned 1 of 1".
   So whether the line reads oddly depends on the brief. "2 of 1" is literally true, and the
   composer's own `how_to_read_this` line explains it, but the strip reads as an error. It is in a hunk of `CandidateSet.jsx` that is not this
   package's, because WP-14.23 edits the same file, so it is **named and not changed**. The fix is
   wording, and the words belong in a record.
4. **A style change keeps the named parti.** If the reader names a diagram and then changes the
   style, the diagram stays in the brief and is re-grouped under whatever nativity it has for the
   new style. If it becomes borrowed and borrowed diagrams are not included, it is shown off-list.
   Clearing it silently would change the reader's brief without a word, which is the rule an
   off-schema budget tier already follows. The server decides whether the pair can be composed.

All seven were red on their first run from a green baseline. Each was restored, and the baseline
was green again afterwards.

**The browser walk carries the journey end to end.** A new block of twelve checks starts on
`tidewater-georgian`'s dossier. It takes the lineage plan type (`side-hall-townhouse`), follows
*start a brief from this plan type*, and holds the link's word to its record's `term` off the
API. It then checks:

- that the address names the style and the parti;
- that the select holds the parti under the nativity the server states;
- that the posted brief carries `parti` and the composer accepts it;
- that the returned candidate carries the `named-by-the-brief` flag in that record's word;
- that the job's own `named_parti` and `named_by_brief` agree with the page, on exactly one
  candidate;
- that a parti no group holds is shown as itself;
- that composing it is refused in the composer's words (*"no parti has that id"*).

The walk reads **406 green, none failed and four COULD NOT EVALUATE, exit 3**. The four are
the four the base already carries: the fallback caption, the stacks, the stoop and the
drawing-set face caption. All four are about the record the walk's bench draws
(`good-03-parlor-drawing-room-house`), and this package touches none of them.
Exit 3 is the walk's own *an unjudged walk is not a green one*, and it is not a pass.

**The walk's first run was red on two of its own new checks, and the defect was the
instrument.** `GET /api/glossary/{id}` answers `{version, term: <record>, …}`, so the block's
first draft read `.term` off the wrapper and compared the page's word with `undefined`. The page
was right both times. The walk already has a reader for that payload, `termOf`, and both checks
use it now. The red was worth having for its own sake: it shows the two checks can fail.

## IV. What was deliberately not done

- **No count literal, no new colour, no definition written in the app.** The link's word, the
  flag and the three nativity words are glossary records. The walk reads each record's `term` off
  the API and holds the page's word to it.
- **`router.js`, `navModel`, `App.jsx` and `client.js` are untouched.** `parti` was already a
  selection key and `api.partis` already took `include_borrowed`.
- **CandidateSet's other hunks are untouched**, including the Spotlight that WP-14.23 removes and
  the count line in finding 3.
- **The walk adds `revise: false` to the post the form makes, and nothing else.** The placed
  revision loop runs for minutes on the proving engine. The flag the block reads is written by the
  composer before any round runs, so the walk does not need the loop.
- **The line for a named parti the set does not hold (`returned: false`) is not driven by the
  walk.** Reaching it needs a brief whose lot drops the named diagram, and the walk has none. It
  is held by a source guard in `candidateOrder.test.mjs`, which reads the JSX for the branch and
  its `why`. That is the weaker form of guard, and it is named here as such.
- **`CLAUDE.md`'s search-index figure is the lead's to move.** The new glossary record takes
  `/api/search/index` from 821 to 822 entries. `workbench/README.md` and `docs/workbench.md` are
  corrected here, and `check_counts.py` names the third site.
