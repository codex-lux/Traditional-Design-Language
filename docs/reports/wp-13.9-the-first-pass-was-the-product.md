# WP-13.9 — the first pass was the product

**Status: COMPLETE (19 September 2026).** Ruled by Lucas the same day, against the bench's own
Tidewater sheet.

Lucas read the Plan Workbench and found sixty drawn findings — most of them the `unreachable`
fatal — beside a revision panel reading `REVISED · 0 ROUNDS · 0 MOVES APPLIED · CONVERGED —
NOTHING LEFT A MOVE COULD ANSWER`. His words:

> During plan solving, there doesn't seem to be any level of recursive self-improvement
> directed towards resolving any of the fatal issues that arise during the generation. So
> what's produced and surfaced is basically a first pass that has all of the problems that the
> program already identified but didn't actually bother to resolve itself. There should be at
> least one or two steps of recursive self-improvement based on the criticisms identified
> before the plan is surfaced to the user.

That screen was four defects, and **none of them was the loop failing at what it had been asked
to do**. Each is below with its measurement.

---

## I. What was on the screen, mechanically

1. **Solve never ran the loop at all.** `re-solve`, an example chip and an undo each ran exactly
   one `POST /api/plan/evaluate` (`PlanWorkbench.jsx:145-173, 270-277, 470`). The loop was
   reachable only from two chips submitting a job. **The panel in the screenshot was a leftover**
   — the `revision_report` of an earlier `revise (proof)` job, riding on a record that had since
   been loaded and re-solved.
2. **On the search engine the door move was never offered.** See §II.
3. **Two placements on one screen.** The sheet's sixty rows were judged on a hill-climb
   placement `typefacts` had refused; the panel's key was measured on a CP placement from the
   job's own separate solve. `RevisionPanel.jsx` admitted "the two can differ" and the reader
   was left holding both.
4. **The `unreachable` sentence was false on five of ten rooms.** See §V.

## II. THE RULING'S FIRST HALF: A STRANDED ROOM WITH A PLACED NEIGHBOUR IS ANSWERABLE ON EITHER ENGINE

`critique.classify` tests `_is_placement` **before** it asks `_intended_move`, and that function
returned `engine != "cp-sat"` for the `unreachable` and `cut-off` kinds. So on the only engine
that produces these fatals in bulk, `add-the-grammar-door` — the move the 1 Sep ruling granted
for exactly this finding — was never offered, and `revise._choose` reads
`assessment["actionable"]` alone.

Measured on `plans/tidewater-georgian-careful.json`, `engine="heuristic"`:

| | classed `placement` | classed `actionable` | classed `architect` |
|---|---|---|---|
| as shipped | **10 of 10** | 0 | 0 |
| the same findings relabelled `cp-sat` | 0 | **9** (`add-the-grammar-door`) | 1 |

All ten carry a non-empty `adjacent_placed`. The one that stays `architect` is `primary`, which
already declares a door to all three of its placed neighbours — the move can only ADD one.

**Four files said otherwise in prose and nothing asserted it.** `CLAUDE.md:3565`,
`PLAN-OF-ACTION.md:1750`, `docs/geometry.md:44` and WP-11.8's own report all carried
"`critique._intended_move` answers every one with `add-the-grammar-door` and the revision loop
runs by default". The *evidence* half re-derives exactly; the *consequence* half described a
counterfactual. It survived eleven days and an adversarial audit because the one test near the
behaviour asserts that `adjacent_placed` is a **list**. All four are corrected, WP-11.8's by an
addendum rather than an overwrite.

**The lever is not lost.** What the old class said — a proof or a wider pool might have seated
the door the author already declared — is still true on the search, so `classify` attaches it to
the row (`lever`, `lever_move`, `lever_why`) and `revise`'s `remaining` publishes it for both
classes. The class says what the loop will DO; the lever says what an engine setting could still
change.

This closes the `unreachable`/`cut-off` half of
`oq/a-placement-finding-is-classed-by-what-the-engine-is-for-five-kinds`. **The other four kinds
are untouched and the question stays open on them.**

## III. THE RULING'S SECOND HALF: THE LOOP READS THE REFUSAL

`build/revise.py` had **no reading of `geometry_report.refused` anywhere**. `_improves` guarded
`could_not_evaluate` and the key. So the loop could move a room, re-place, watch the key fall,
accept, and hand back a record WP-13.4 forbids any surface to draw — reporting a lower key on it.

A refusal is the drawing's `fatal`, and it is guarded the way a fatal is:

```python
if _newly_refused(new, old):
    return False
```

**The direction is the point.** A placement already refused when the loop starts may still be
improved — refused → refused on a lower key is accepted — because refusing to work on a refused
house would leave the reader with the first pass and nothing else, which is the complaint. What
is refused is *making* one. Both shipped plans are refused before the loop starts, so this is
the live case rather than a shape.

The report carries `placement_refused: {before, after}` and `summary.refused_before/after`; a
round rolled back for a new refusal says `rolled_back_by_refusal` rather than wearing the
measurement's verdict, which would be a refusal with one message for two causes.

## IV. THE ROUNDS RUN BEFORE THE PLAN IS SURFACED

`evaluate.evaluate` takes `revise_rounds` (default **0**) and `revise_budget_s`. On an explicit
solve the bench sends 2; the wall drag sends none, because a gesture cannot wait for a loop any
more than it can wait for a proof. **This supersedes WP-9.3's "a per-edit critique: deliberately
not done" for the explicit solve only**, on the 19 Sep instruction.

**It is inline rather than the job route because of WP-6.4's rule — one drawing set is one
building.** The job hands its record back stripped and the bench re-solves it, which is what put
sixty findings of one placement beside a key measured on another. Here the loop's final PLACED
record is what `check_plan` judges, what `placement_summary` is projected from, and what
`rooms_meta` reads; the declared record rides beside it as `revised_plan` for the bench to load
as one undo step.

The loop runs on **the engine that placed**, never `auto`: a round is judged by re-placing and
comparing keys, so judging on another engine compares two houses — and `auto` would re-attempt
the proof at 25 s inside every round on a record where it has just been measured to fall back.

### The budget was wrong once, and the correction is the measurement

`BUDGET_REVISE_INLINE_S` was first set to **50.0** on the reasoning that fifty seconds is "two
interactive proofs plus their checks". Measured at `engine="auto"`, the loop then ran for
**69.6 s**: `revise()` tests its budget at the TOP of each round, so round one ended at about
35 s, 35 is less than 50, and round two started and ran to 70. **A ceiling that is not a ceiling
is worse than none, because it reads as one.**

**30.0 is derived from that measurement rather than chosen**: one round on a CP placement costs
about 35 s, so a second round starts only where the first was cheaper than this.

| engine | rounds run | loop time | stop reason |
|---|---|---|---|
| `heuristic` | 2 | **2.9 s** | round-cap |
| `auto` → CP-SAT | 1 | **36.4 s** | budget |

So the inline loop runs both rounds where they are nearly free and one where each costs a proof,
and says so. That is the ruling's "at least one or two" landing on either engine rather than a
number that means two on one of them and a minute of somebody's time on the other. The chip
routes keep their own far larger budgets: a job is not a person waiting.

## V. THE `unreachable` SENTENCE WAS FALSE ON FIVE OF TEN ROOMS

It read "The record declares N door(s) to it and the placement realised none of them" for every
stranded room. Measured on the Tidewater plan at `engine="heuristic"`:

| what the placement did | rooms | the sentence they were given |
|---|---|---|
| realised **none** of the declared doors | 4 | correct |
| realised **all** of them | 3 | **false** |
| realised **some** | 2 | **false** |

`primary` declares three doors, its `unplaced_pairs` is empty — all three were placed — and it
was told none were. The room is cut off because the cluster it belongs to is. **The number to
say it with was already in hand**: `unplaced_pairs` is computed by the same loop and was attached
to the finding as evidence while the prose contradicted it. Three sentences now, and
`realised_doors` rides as evidence.

## VII. What was deliberately not done

- **A root-cause finding naming the one unseated pair that strands a cluster.** On this plan
  `('passage','stair')` strands the stair and the library, and four pairs on `upperpassage`
  strand the upper floor — ten fatals a reader has to reconstruct into two causes.
  `plan_check` already has the shape for it (`outside-is-only-an-appendage`). Left out because
  it is a new finding kind and this package already moves every drawn statement; it is the
  obvious next package.
- **Rewriting `_is_placement`'s other four engine-name kinds.** `drawn-vs-declared`,
  `stack-broken`, `landing-off-well` and `stack-unplaced` keep the reading they had. The ruling
  was given about the stranded room; extending it by analogy is the laundering this corpus
  refuses.
- **Running the rounds on the wall drag, or on undo.** The drag cannot wait; an undo that
  revised would re-apply the revision it was pressed to remove.
- **Making the chip routes return the loop's own placement.** They still strip and re-solve, so
  the two-placements divergence survives there — raised as
  `oq/the-chip-driven-revision-is-judged-on-a-placement-the-sheet-does-not-draw` rather than
  fixed, because it is a second surface's contract and this package already changed one.
- **Lowering the interactive cost of a CP round.** 36.4 s of somebody's wait buys one round and
  one move on the Tidewater plan. Solving that means a cheaper re-place, which is the placer's
  question and not the loop's.

## VIII. The guards, and the one that was blind

Twenty-four mutations, each asserted to have LANDED before its colour was believed and each file
restored byte-for-byte in a `finally`. **Twenty-three red on the first run; one was blind.**

`test_the_rounds_are_bounded_and_an_unreadable_value_asks_for_none` posted `revise_rounds: 999`
and asserted the report came back inside `core.REVISE_MAX_ROUNDS` — **which passes with the
route's bound deleted**, because `core.revise_plan` bounds `rounds` itself before the loop ever
runs. It was asserting the inner bound through the outer one and could not fail. Re-cut onto the
reader itself (`app._revise_rounds`, `app._revise_budget` as pure functions), where what the
route decides and nothing else does — that 0 is expressible, and that an unreadable value means
none rather than the default — can actually go red. Three further mutations then bit it.

**And one of this package's own new assertions was vacuous when written**: a loop in
`test_no_round_opened_a_fatal` read `assert not rd.get("opened") or all(i not in ... for i in [])`,
and `all()` over an empty generator is True, so that half could not fail at any state of the
code. Removed rather than repaired, with the reason in the test's docstring.

`tests/test_critique.py` (5), `tests/test_revise.py` (9), `tests/test_plan_check_unreachable.py`
(6), `workbench/server/tests/test_inline_revision.py` (10), `workbench/app/src/revision.test.mjs`
(4), and five new checks in the browser walk.

### The five walk checks are UNREACHABLE today, and that is pre-existing

**The browser walk throws before it reaches them, and it does so identically on a `git archive`
control of HEAD**: eight checks, then `TimeoutError` on `svg[role="img"]`. The cause is WP-13.4
working as ruled -- `tidewater-georgian-careful` is refused on `auto`, so `/api/plan/evaluate`
answers with `placement_refused` and no `placement`, `drawable` is false, and the conflict set
stands where the plate would be. Nothing after that line in the walk runs, on either tree. **It
is not this package's**, and this package deliberately does not fix it: making the walk judge a
refused record is its own ruling about what the walk is for.

So the five checks added here are written against a surface the walk cannot currently reach.
They are kept rather than deleted -- they bite the moment that throw is fixed, and deleting them
would lose the statement -- but **they are unverified by the walk and this report may not claim
otherwise.**

**They were verified live by a focused probe instead**, which waits on `[data-panel="revision"]`
rather than the plate, and all eight of its checks pass against a real browser and a real
server. The probe is not committed: it duplicates the walk's checks, and a second walk is a
second thing to keep current.

### AND THE PROBE FOUND A DEFECT BOTH SUITES WERE STRUCTURALLY BLIND TO

The panel read:

> Key serious 61 -> 59 . minor 106 -> 110 (on the proved placement, 36.6 s). **The sheet above
> is the placement this key was measured on** -- the loop's own, drawn as it ended.
>
> The placement the loop stopped on is still refused -- bearing, hearth, tiling are downgraded:
> no sheet, export or model is drawn from it.

**Two sentences, one screen, and the first promises a sheet the second says does not exist.** On
a refused placement there is no plate above the panel at all. Every assertion in `tests/`,
`workbench/server/tests/` and `revision.test.mjs` was about the REPORT -- the rounds, the counts,
the fields -- and the defect was in the sentence rendered from it, which is the one thing none of
them reads. The noun follows `refusedAfter` now ("the findings above", which is true either way),
with a JS guard on the adapter's ability to see the refusal and the walk check re-cut onto the
claim the two wordings share.

**Render the surface and read it** is this repository's highest-yield technique, and it earned
itself again here.


**The walk's click-to-sheet wait went 90 s → 150 s**, and that is measured rather than
precautionary: an example chip is an explicit solve now, so the path is a 25.9 s solve plus a
36.4 s round before the sheet is drawn. **And this package weakened one of the walk's existing
checks before it strengthened it**: the panel is now already on the page when the `revise
(search)` chip is clicked, so waiting for `/stopped:|converged/` alone would have matched the
SOLVE's panel on the first tick and asserted nothing about the chip at all. The discriminator is
the sentence each path makes, and the chip's — "a fresh solve … the two can differ" — is now
required before that loop exits.
