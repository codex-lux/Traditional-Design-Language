# WP-1.1 — Constraint rule language and a worked migration

*Executed 23 August 2026, overnight autonomous session, immediately following WP-0.3, as the first package of Phase 1 ("spine first," per this session's scoping instructions).*

## What was built

`schema/constraint.schema.json` — the standalone shape of one migrated constraint: `id` / `kind` / `severity` / `statement` / `scope` required, `deprecated_in_favour_of` and `test` optional. Reuses the fault corpus's `test` object pattern per OQ 24's ruling, extended with a `one-of` direction (for categorical/enumerable rules the fault schema never needed) and a `scope` field (`plan` / `elevation` / `site` / `section` / `judgment`) so a downstream tool can ask which of a style's hard constraints it can actually evaluate from what it has. Deliberately not `$ref`'d from `schema/style-node.schema.json` — no schema file in this repository cross-references another, and `build/validate.py`'s bare `jsonschema.validate()` call has no resolver configured, so a cross-file `$ref` would be unreliable rather than caught. `style-node.schema.json`'s inline `constraints.items.test` stays loosely typed for that reason, with a description pointing at the real schema.

`build/constraint_vocabulary.py` — the named variable vocabulary a `test.expression` may reference. Started at 30 entries (seeded before migration began); grew to 68 while actually migrating the worked example, because writing tests against real constraint text surfaces gaps a vocabulary designed in the abstract wouldn't predict. Every addition is used by at least one real constraint in this migration, most by two or more.

`build/check_constraints.py` — validates every migrated constraint (anything carrying an `id`) against the schema, checks id uniqueness and the `<style>.c##` pattern corpus-wide, enforces that `scope: judgment` constraints carry no test and that every `hard`, non-judgment constraint does, checks direction-specific field shape (`between` needs both bounds, `one-of` needs a `set` and no threshold), and warns — not errors, the same courtesy the vocabulary's own docstring asks of a migration-batch agent — on any expression referencing an unrecognised variable. Wired into `build/check_all.py` as the corpus's fourteenth check, immediately after `check_kits.py`.

`build/migrate_constraints_wp1_1.py` — the worked-example migration itself, run once. Not a reusable tool; it's this run's hand-authored per-constraint data (scope, and a test where one is honest), applied mechanically so the id-numbering and the merge are auditable and the run is reproducible if a source statement gets corrected later. Migrated the `english-classical` family (7 style nodes: `adam-style`, `english-baroque`, `english-georgian` and its two variants, `english-palladian`, `regency`) and the `american-colonial` family (21 style/variant nodes across the Dutch, French, Georgian, German, New England, and Spanish colonial branches) — 28 nodes, 140 constraints (5 each, none of the constraints these families' family-rank nodes themselves carry any, so the family nodes contributed 0).

`docs/constraints.md` — the rule language explained, the vocabulary's growth and reasoning, and a close read of what the migration actually produced pattern by pattern: clean single-clause tests, compound statements tested-in-part with the leftover clause noted, a genuine disjunction resolved by finding a shared safe bound (`spanish-colonial-american`'s roof pitch) versus one left honestly untested because no such bound exists (`creole-cottage-vernacular`'s galerie-or-abat-vent shelter), one deliberately loose-but-exact union test (`mid-atlantic-georgian`'s two-material wall thickness, whose ranges are contiguous) versus one loose-and-imprecise test flagged as such (`spanish-colonial-american`'s adobe-vs-rubble slenderness ratio, whose ranges are not).

`tests/test_constraints.py` (6 tests) — pins a real migrated constraint's schema conformance; pins the worked example's exact split (140 migrated, 106 tested, 34 judgment) so a future migration script or checker edit that silently changes those numbers gets caught; pins the vocabulary's expression checker correctly flags an unknown variable and correctly does not flag `abs()` or a real vocabulary name; pins `check_constraints.py` errors on a duplicate id across two nodes and on a hard non-judgment constraint with its test stripped, using the same backup/corrupt/restore-in-`finally` pattern `test_kit_cascade.py` established for round-tripping a real corpus file through a deliberately broken copy.

## What was found

**The vocabulary more than doubled during authoring, not before it.** 30 entries were enough to validate the schema design against a handful of example constraints while building the checker; they were not enough to migrate two real families. Every one of the 38 additions traces to a specific constraint statement that needed it, and the two clearest patterns worth naming for whoever migrates the next family: roof planes should be named by *position* (`roof_slope_lower_deg`/`roof_slope_upper_deg`, nearer-eave vs. nearer-ridge) rather than by steepness, because which one is steeper flips between a gambrel (lower is steeper) and a gallery-roof break (lower is shallower) — and a single measurement concept recurring under different regional names (`gallery_depth_ft` covering a Louisiana galerie, a Charleston piazza, a Spanish corredor, and a Dutch sprung-eave porch) is worth one shared variable, not four regional aliases.

**Two constraints needed a scalar test that couldn't be made fully exact, and the difference between them is instructive.** `mid-atlantic-georgian`'s wall-thickness rule gives two material-specific ranges that turn out to be contiguous (18–24in stone, 13–18in brick, meeting exactly at 18in) — their union is an *exact* test, not a compromise, because nothing in the union falls outside both individual ranges. `spanish-colonial-american`'s wall-slenderness rule gives adobe a 10x ceiling and rubble a stricter 8x, and these do *not* meet cleanly — a rubble wall at 9x would pass a test written to the looser bound while still violating its own material's real limit. The schema has no way to express "conditional on which material," so the second case tests at the loose bound and says so in its `note`, rather than either pretending precision it doesn't have or refusing to test at all. Recorded in `docs/constraints.md` as the general pattern: check whether two disjunctive ranges are actually contiguous before deciding a union test is exact.

**A genuine disjunction sometimes has a safe scalar bound hiding in the same sentence, and sometimes doesn't.** `spanish-colonial-american`'s roof-pitch rule ("either flat... or 3:12 to 5:12 tile") also states an unconditional ceiling ("pitches above 6:12 are foreign to the tradition") that covers both branches without a false accept — tests cleanly at `at-most 6`. `creole-cottage-vernacular`'s shelter rule ("either a posted galerie not less than 6ft deep... or an abat-vent projecting 30–48in...") has no such shared figure; testing either branch alone would flag a validly-built-the-other-way house as a violation. The first got a test; the second got `scope: judgment`. Worth watching for in every family: read the whole sentence for a bound that survives the "or," not just the two branches.

**A recurring, specific reason kept judgment-scoping constraints that otherwise had numbers in them: date-conditional rules.** Sash-pattern-by-period, fanlight-date, and similar constraints appear across nearly every Georgian-descended style in this migration (`georgian-colonial-american`, `mid-atlantic-georgian`, `new-england-georgian`, `tidewater-georgian`, `german-pennsylvania-colonial`, `new-england-colonial`, `saltbox-colonial` all carry at least one). Every one of these is `scope: judgment` not because the rule is unmeasurable but because OQ 22 (no date-conditional resolution mechanism) blocks evaluating it — a structurally different reason from the other three judgment cases (per-room universal quantifiers, purely qualitative claims, unbridgeable disjunctions). Nothing currently distinguishes "judgment because OQ 22" from "judgment for a real reason" on the record; raised as new OQ 27.

## What was deliberately not done

**The remaining ~520 constraints across ~25 families were not migrated.** This package's brief was explicitly to build the schema/vocabulary/checker and migrate a worked example, not the whole corpus — `docs/open-questions.md`'s item 24 originally overstated this as "the migration of all 660 constraints," which was corrected in this session to name the actual worked-example scope, since leaving an inflated completion claim standing would be exactly the kind of doc-drift WP-0.2 and WP-0.3 existed to catch. The remaining families are unstarted and should follow `PLAN-OF-ACTION.md`'s per-family hand-off brief, using the schema and vocabulary this package built and extending the vocabulary only where a genuine gap turns up.

**WP-1.2 (validator reads constraints) was not started.** It depends on this package and, per the "spine first" scoping, is the next package in the dependency order — `build/check_constraints.py` validates the *authoring* of a constraint; nothing downstream (`plan_check.py`, `compose.py`, `geometry.py`) evaluates one yet against an actual plan or elevation.

**No `blocked_by` tag was added to the OQ-22-blocked judgment constraints.** Recorded as new OQ 27 instead of decided unilaterally, since it's a corpus-wide authoring-convention question the next migration batches need answered consistently, not a call this package's own scope should make alone.

**Vocabulary consolidation was not attempted.** 68 entries after two families is a real number worth watching, not yet a problem — `docs/constraints.md` says explicitly that whether it keeps growing roughly linearly or levels off is one data point short of being decidable, and flags it as something for whoever runs the next batch to notice rather than something this package should have an opinion on yet.

## New open question raised

**OQ 27 (new).** A `scope: judgment` constraint blocked purely by OQ 22 (no date-conditional resolution) looks identical, on the record, to one that's judgment for a genuinely different reason — a per-room universal claim, a purely qualitative statement, an unbridgeable disjunction. Should these be tagged distinguishably at migration time (e.g. `blocked_by: "OQ-22"`), so that resolving OQ 22 later can find and convert them without a full re-read of every judgment-scope constraint's statement? Not decided here because it's a convention the remaining ~25 families' migration batches all need to follow consistently — worth settling before the next batch runs. Added to `docs/open-questions.md`.
