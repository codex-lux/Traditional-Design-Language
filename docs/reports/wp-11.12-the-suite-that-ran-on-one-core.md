# WP-11.12 — the suite that ran on one core

*7 September 2026. Raised by Lucas against a screenshot of the corpus job: "the corpus check
has ballooned to now taking upwards of 40 mins per PR… is there any way to consolidate this?"*

---

## I. What was measured before anything was changed

The instruction was to consolidate, and the first thing worth recording is that consolidation
was the wrong shape for the problem — which only became visible by measuring rather than by
reading the check list and looking for something to merge.

Run `33908079938`, the last green push to main, per job:

| job | wall |
|---|---|
| `corpus — check_all.py` | **39 min 32 s** (one step) |
| `workbench — server tests + app build` | 8 min 17 s |
| `docker build` | 55 s |

So the corpus job *was* the wall-clock of a pull request; nothing else came close. Reproduced
locally on a four-core container that ran the whole thing in 2,267 s against CI's 2,372 — about
5% apart, which is close enough that the local split is the CI split:

| | seconds | share |
|---|---|---|
| `pytest tests/` | **2,070** | **87 %** |
| the 44 checkers | 197 | 8 % |
| everything else | ~5 | — |

**Nothing in the suite is slow.** The 44 checkers, timed one by one, are 197 s in total and the
worst of them is 49 s. The tests are 1,570 of them at an average of 1.3 s. What was wrong is
that 2,267 s of independent work ran on one core, and had done since the day `check_all.py` was
written, when it was three minutes.

There was nothing to consolidate. There were two things to do: stop paying for work that was
never needed, and stop doing the rest of it in a queue.

## II. The 46 seconds that were a convenience wrapper

`jsonschema.validate(instance, schema)` is a wrapper that, on every call, looks up the validator
class for the schema, runs `check_schema` over the whole schema, and constructs a fresh
validator. Five checkers called it in a loop.

| checker | records | before | after |
|---|---|---|---|
| `check_assets.py` | 1,850 assets | **35.70 s** | **0.59 s** |
| `validate.py` | 164 style nodes | 5.93 s | 0.40 s |
| `check_kits.py` | 159 kits | 6.25 s | 1.93 s |
| `check_orders.py` | 57 packs | 2.27 s | 0.38 s |
| `check_constraints.py` | 660 constraints | 0.78 s | 0.18 s |

`check_assets.py` was **18% of the entire checker suite** and 36 of its 36 seconds were the
wrapper: compiled once, validating all 1,850 records costs 0.35 s. `build/schema_validators.py`
is the one spelling of the fix.

**This defect was already recorded in CLAUDE.md.** WP-10.1 measured the same wrapper at 60.5 ms
a call, 17.9% of `/api/plan/evaluate`, and closed with *"measure what you add to the hot path
BEFORE you add it."* What that entry did not say — because it was answering a question about one
route — is that the same wrapper was being paid about 2,400 times a build by the checkers one
directory over. The companion to that lesson is: **then go and look for the shape somewhere
else.** A `grep` for the call would have found all five in ten seconds, on any day in the past
year.

**The risk in the fix was never the speed, it was the message.** `validate()` raises
`best_match(iter_errors(instance))` — not the first error, the *best* one — and every one of
these checkers puts `e.message` in front of a person and into a test. A faster validator that
chose a different error would be a silent change to every failure this corpus can produce, and
nothing in the tree would have noticed. `raise_first()` is `best_match` and a raise, and
`tests/test_schema_validators.py` holds the two against each other on real records from every
schema the checkers loop over, with each required property removed in turn — because one
hand-picked break exercises one branch of the heuristic and reads as proof about all of them.

## III. The other 2,220 seconds: six jobs, not one

`build/check_all.py --shard i/N` partitions the run. 123 units — every `CHECKS` entry and every
`tests/test_*.py` file — packed longest-processing-time-first onto N shards.

    n=1   makespan  2490s   (41.5 min)     <- what CI was doing
    n=4             623s    (10.4 min)
    n=5             498s     (8.3 min)
    n=6             415s     (6.9 min)     <- shipped
    n=7             400s     (6.7 min)
    n=8             400s     (6.7 min)

**Six is measured, not chosen.** The makespan is bounded below by the largest indivisible unit,
and `tests/test_score.py` is 400 s on its own, so the curve goes flat at seven and a seventh
runner buys fifteen seconds. Six is also free: 6 × (415 s + ~30 s of setup) is 45 runner minutes
against the 41 the single job was already spending, so the wall clock falls sixfold and the bill
does not move. `--list-units` prints the assignment and the cost table's figure for each unit,
so the next person to ask "would seven help?" can answer it in a second rather than by argument.

**The split is by JOB, and that is the finding rather than an implementation detail.** Six test
files mutate repository data in place and restore it in a `finally` — `test_kit_cascade` writes
a kit, `test_manifest_io` and `test_render_profile` truncate `assets/manifest.json`,
`test_ontology` rewrites `elements/slots.json`, `test_constraints` a style file,
`test_open_question_ids` the register. `pytest -n auto` in one checkout would let one worker
read a file while another has it truncated: intermittent, and blamed on the reader. Separate
GitHub jobs have separate checkouts, and inside a shard the tests still run serially in one
pytest process, so **the isolation this suite already relies on is untouched** — which is also
why the change needed no edit to any existing test.

## IV. The failure this could have introduced, and what stops it

A unit assigned to no shard runs nowhere, and a suite that runs nowhere reports success. This
repository has shipped that defect under several names: the CI id gate whose loop body was
unreachable, the gazetteer ratchet that went quiet for want of a runtime, the walk CLAUDE.md
called a guard while no job ran it. A hand-written split — "shard 1 gets these twenty files" —
is that defect with a maintenance schedule.

So nothing is enumerated. `units()` globs `tests/test_*.py` and reads `CHECKS`; `assign()` places
every unit at the argmin of a load vector, which is total onto `0..N-1`. A unit is in exactly one
shard *by construction*, not by anyone remembering to add it.

`tests/test_check_all_shards.py` holds that anyway, and was mutation-checked four ways — each
mutation asserted to have landed before the colour was believed:

| mutation | caught by |
|---|---|
| `assign()` silently drops one unit | partition test, 2 failures |
| `ci.yml` matrix `[1..5]` against `--shard i/6` | the CI-agreement test |
| `run()` stops deriving what it was assigned | the source-read test |
| a cost-table key naming a file that no longer exists | the stale-key test |

The second is the one worth naming. **The matrix and the `--shard i/N` argument are two
independent numbers in one file and nothing else compares them**, and the failure is silent in
the dangerous direction: five shards against a denominator of six runs five sixths of the suite
and every shard is green.

Beside it, `run()` counts what it reported against what it was assigned — `2 + len(my_checks) +
(1 if my_files else 0) + len(my_suites)` — exactly as the whole run counts itself against
`TOTAL_CHECKS`, so a unit lost between `assign()` and `run()` fails the build instead of
vanishing.

**The empirical proof that the partition is real**: six shards, run in six isolated checkouts,
collected **1,923 tests between them** — exactly what the single run collects, unit for unit,
with the three permitted N/EV states landing one each in shards 2, 3 and 6. Measured twice: at
five shards before merging main it was 201 + 567 + 262 + 213 + 327 = 1,570 against a single run
of 1,570.

**AND THE SUITE CAUGHT THE ONE THING THIS PACKAGE BROKE.** The open-question id gate was lifted
out of `ci.yml` into `.github/scripts/oq_ids_do_not_collide.sh` — it answers the same for all six
shards and running it six times is six chances at a rate limit — and
`tests/test_open_question_ids.py` sliced that shell **out of the YAML by string index** in order
to run it against stub registers. It raised `ValueError: substring not found`, in shard 4, on a
guard whose own header records that it exists because *"a guard nobody runs is a comment."* The
test is coupled to the script now, which is the thing CI executes, and a new assertion holds
`ci.yml` to still calling it — correct-and-unreferenced being the failure the first one cannot
see. Both were mutation-checked: neutering the collision branch fails two, removing the call from
`ci.yml` fails the third.

## IV-a. The hazard demonstrated itself, by accident

The verification harness copied the tree with `rsync`, which is not installed in this
container. Without a `|| cp -r` fallback the six copies were never made, every `cd` into a
shard directory failed, and **all six shards ran concurrently in the one live checkout** —
which is precisely the arrangement §III refuses. It produced, within one run, exactly the two
failures the design predicts:

    FAIL  build.py
      FileNotFoundError: 'kits/arts-and-crafts-american.kit.json.tmp'
                      -> 'kits/arts-and-crafts-american.kit.json'

    FAIL  pytest tests/ (12 of 78 files)
      test_every_revised_plan_validates_and_keeps_the_briefs_must_have_rooms

Four shards' `build.py` raced on each other's `.tmp` files, and one shard's test failed
because another shard had a corpus file open mid-mutation. **Neither failure names its cause**:
the first reads as a corrupt kit and the second as a composer regression, and a person handed
either one would go looking in the wrong file. That is the whole argument against sharing a
checkout, and it arrived as evidence rather than as reasoning.

It is also the case for the `finally` blocks those six test files carry: after six shards had
fought over the tree for twenty minutes, `git status` showed only the files this package edits
and no stray `.tmp`. The restores held; what did not hold was everything reading while they ran.

## IV-b. The one thing this package shipped broken, and how it was seen

`--shard 1/1` is supposed to be the run `make check` always did, byte for byte: a shard
holding every test file invokes `pytest tests/` rather than a file list. It did not. `assign()`
hands a shard its files in longest-first order and the branch compared that list against a
sorted one, so at 1/1 — which holds all 78 — the comparison was **False**, and the unsharded run
invoked pytest with 78 explicit paths in cost order.

**All 1,923 tests ran and passed.** Every existing guard was green, the partition test was green,
the count guard was green. What it was not was the run this script did before it could shard,
which the module docstring promises in those words.

**The only witness was a line of output**: `=== pytest tests/ (78 of 78 files) ===`, in the log
of a forty-minute verification run. A claim whose only witness is a line nobody diffs is not
guarded — so the decision is a pure function now, `pytest_target()`, with three tests over it,
and the first of them refuses to run at all if `assign()` ever starts returning sorted files,
because at that point it could no longer tell a sorted comparison from an unsorted one and would
be green without being about anything. Reverting the sort fails two of the three.

The order matters beyond tidiness: alphabetical is what `pytest tests/` collects in, and it is
the order every claim in this suite about order-independence was measured against —
`TestTheComposerIsDeterministic`'s docstring says exactly that about its own file.

## V. Two things kept deliberately

**`corpus — check_all.py` still exists**, as an aggregate job that `needs` the matrix. Branch
protection and Railway's "Wait for CI" gate are configured against that name, and a required
status check that stops existing stops being required — silently. It carries `if: always()` and
an explicit result test, because a *needed* job that fails leaves this one *skipped*, and a
skipped job is not a failed one to a protection rule.

**`build.py` frames every shard rather than being a unit.** It writes `dist/taxonomy.json`, which
`check_kits`, `check_addresses` and `check_inheritance` all read — a shard that got a reader
without the writer would validate whatever artefact the checkout happened to carry, which is the
exact defect the audit of 25 Aug found when `build.py` ran last. Its closing run still proves
nothing mutated the artefact, and under sharding it proves that of the shard's own checkers,
which is what it can honestly prove. Both cost 0.84 s a shard.

## VI. What was deliberately not done

**No `pytest-xdist`, in any form.** It is installed, it would have been three characters of
config, and §III is why not. The six mutating files could have been quarantined with a marker
and a serial first pass — but the safety of that arrangement then rests on every future test
author remembering the marker, and the failure mode is an intermittent red blamed on whichever
test happened to be reading. The job split needs nobody to remember anything.

**No caching of `compose()`.** It is the real shape of the test suite's cost — roughly 60% of the
2,070 s is a few dozen tests each composing the same brief from scratch at ~30 s — and a
module-level memo keyed on the brief, in the shape `geometry._SOLVE_CACHE` already has, would
have taken the suite under ten minutes on one core. It is refused because
`TestTheComposerIsDeterministic` exists: `test_composing_one_brief_does_not_change_another_s_result`
would pass **trivially** against a cache, and its own docstring says an audit already proved it
vacuous once when a session-scoped fixture polluted it. A cache would make three guards
unfailable to buy time that six runners buy for nothing. Recorded rather than built, and it is
the reason the makespan floor is 400 s: `tests/test_score.py` is 400 s because it composes
eleven times.

**No splitting of a test file across shards.** Node-id-level units would take the floor below
400 s, at the cost of a unit list that changes with every test added and a cost table keyed on
node ids. The flat spot at seven shards says the win is fifteen seconds.

**No extension of `check_counts.py` to the cost table.** That checker guards numbers *derived
from the corpus*, and a wall-clock second measured on one machine is not one. A stale figure
there costs balance and can cost nothing else, because `assign()` is total whatever the table
says — this is stated in the file, in the module, and in the test that permits an uncosted new
unit while refusing a stray one.

## VII. Verification

| | |
|---|---|
| `python3 build/check_all.py` (unsharded, the authoritative run) | **exit 0** — `45 of 48 checks passed; 3 COULD NOT EVALUATE`, 2,665 s |
| six shards in six isolated checkouts | all exit 0; **1,923 collected between them**, the single run's exact total |
| the identity CLAUDE.md teaches | `TOTAL − 3 = len(CHECKS)` — 48 − 3 = 45, printed |
| shard balance at six | 415 s expected, every shard, `--list-units` |
| mutation-checked guards | 8, each mutation asserted to have LANDED before the colour was read |

**Both of those runs collected 1,923 and CLAUDE.md publishes 1,927**, and the four between them
are this section's own: the three `pytest_target` guards and the refresh-block guard, all written
after the full run and in response to what it exposed (§IV-b). They were run on their own — 18 in
`test_check_all_shards.py`, green, and each mutation-checked. Saying "1,927 verified" would have
been one sentence and false, which is the shape §IV-b is about.

The three unjudged are the documented ones — both CAD selftests and the fastapi suite — and
under sharding they land one each in shards 2, 3 and 6 rather than three in one log, which is
why CI's allowlist is a NAMED LIST and not a count. A count would have to be re-derived per
shard from a cost table that is explicitly a hint.

## VIII. What this leaves open

`build/check_costs.json` is the first thing in this repository that is deliberately *allowed* to
rot, and saying so out loud is the honest half. It cannot make a check not run; it can only make
one shard finish five minutes after the others, and the only symptom is a slower CI that nobody
attributes to a table. Every shard prints a refreshed block in the file's own shape at the end of
its run, so the refresh is a paste — but nothing makes anybody do it. If the balance is ever
visibly wrong, `--list-units` says so immediately and this is a two-minute fix; the open question
is whether a hint nobody is obliged to refresh stays useful for a year. No open question was
raised for it, because there is no ruling to take: it is a maintenance habit, and the file says
which one.
