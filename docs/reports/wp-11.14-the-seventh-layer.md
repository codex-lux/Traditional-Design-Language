# WP-11.14 — the seventh layer, and the fixture that was not the obstacle

*8 September 2026. Branch `claude/georgian-tidewater-plan-analysis-qbwmqs`. Every corpus figure
is `engine="heuristic"`, which is deterministic, and says so. The shipped corpus is
BYTE-IDENTICAL: all sixteen sheets hash `4cfba3a0885ddccb` before and after, measured on a
`git archive HEAD` checkout and on the working tree.*

---

## I. What was wrong

WP-11.9 taught six layers below the placer about massing elements. **The drawing was not one of
them.** WP-11.13 found it by rendering the tagged plan that package made provable and looking at
the sheet: two exterior doors, each with its sill and its swing arc, in open space north of the
whole building, attached to nothing.

Measured on the hand-tagged `tidewater-georgian-careful`:

| | before | after |
|---|---|---|
| exterior doors misplaced | **2** (by 12.00 and 8.98 ft, CP placement) | **0** |
| windows drawn | 7 | **11** |
| windows refused as off-footprint | 16 | **11** |

The 16 refusals split, and the split is the deliverable rather than the total: **5 stood on
their own element's face and were dropped**, and **11 were correct refusals** — the placement
put those rooms inland, which is what that count is for. The fix recovers exactly the 5 and
touches none of the 11.

## II. Two causes wearing one symptom

They are worth keeping apart, because only one of them is about elements:

**`_boundary_wall` asked whether a room touched the FOOTPRINT.** On a dependency at x = −30 that
satisfied `x <= tol` for reasons of *sign* rather than of geometry, and matched nothing on the
other three faces — so a window on a real exterior wall was refused. It takes the room's own
element box now, from `elements.bounds_index`: **the same reader `openings.py` has used since
WP-11.9**, so the drawing and the placer answer "which of this room's walls are exterior" with
one function rather than two.

**`render()` drew every exterior opening at `0` / `W` / `H`.** The entry carried a position
ALONG the wall and nothing across it — because on an INTERIOR entry `at_ft` already means the
perpendicular, and one key cannot mean both. `edge_ft` is that coordinate, and **its fallback is
the ROOM's own face, never the footprint's**, which is why the fix is the identity on a
one-rectangle house rather than a change to be checked. The interior branch three lines above
had been right all along and is the model the fix copies.

## III. The obstacle WP-11.13 named was not an obstacle

That package refused to do this work because adding a key to `derive_openings`' output changes
the shape the frozen `tests/fixtures/sheet_symbols/` contract compares — and regenerating that
fixture re-solves the placement on `auto`, which its own README measures at **825 insertions and
804 deletions on the pristine tree with no code change at all**.

**`freeze()` re-solves only to obtain the ROOMS.** `expected` is then derived from them, and the
rooms are already committed: they are contract INPUT. So `expected` is a pure function of what
is already in the file, and re-deriving it touches no solver.

`generate.py --expected-only` does exactly that. Verified **before it was used**, which is the
property that makes it trustworthy: run against the *pristine* renderer it is a byte-for-byte
no-op on both fixtures. Run against this package it produces **39 insertions and 0 deletions** —
the added keys, and nothing else.

That answers item 2 of `oq/an-exterior-door-is-drawn-on-the-footprints-wall-and-not-its-rooms`
("what does the frozen fixture become?") without touching the frozen placement, and it is
available to every later package that changes a renderer's output shape.

## IV. Both renderers, and what the fixture cannot hold

`derive.js` had the identical construct — and its own docstring stated it as intended
behaviour: *"plus exterior doors as openings on the footprint edge."* Its `boundaryWall` was
already **returning** the perpendicular as `at`, and both callers threw it away to recompute
`0`/`W`/`H` inline.

**The frozen fixtures cannot hold the two to one answer here**, because no plan in the corpus
carries a `block` tag and every fixture therefore has one element. So the contract for this case
is hand-built on both sides — `tests/test_exterior_faces.py` and
`workbench/app/src/derive.test.mjs` assert the same three numbers on the same two rectangles,
on WP-11.10's stated precedent for exactly this situation.

## V. The audit of this package's own guards

Six mutations, each **asserted to have landed** before the suite ran. Five bit at once. **The
sixth did not, and it was the one that mattered**: *the drawing ignores `edge_ft`* — the single
line that actually put the doors in mid-air — passed every test in the file.

Every assertion read `derive_openings`' **output**; none read the **drawing**. That is
WP-11.10's own finding, one package later and in the same file: *"the first guard could not
fail: a test reading `derive_openings` directly stayed green with `render()`'s call site
reverted."*

Closing it took two goes, and the first was also blind:

- A test that renders the tagged plan twice, once with `edge_ft` stripped, and requires the
  plates to differ. **It stripped both `exterior` and `windows` at once**, so a mutation to the
  door path alone still moved the plate via the windows and the test passed. It strips **one key
  at a time** now.
- And the code was genuinely wrong in a way the mutation exposed: `_frame` read `d["edge_ft"]`
  while `_door` read a local, so reverting either still moved the other. **One opening has one
  face**; the edge is computed once and handed to both, which is better code and is what makes
  the guard able to fail at all.

## VI. And a third guard read a literal signature

`tests/test_appendages.py::test_both_renderers_read_the_record_and_derive_nothing` pinned
`"def derive_openings(rooms, W, H, tol=0.6, appendages=None):"` verbatim, and its JS twin the
same way — so adding an argument AFTER `appendages` broke a guard that has nothing to do with
massing elements. Its own comment says what it means: *"both take the appendage into the door
lookup, in the same argument position."* It reads the signature's PARAMETER ORDER now
(`inspect.signature` on the Python side, a regex over the parameter list on the JS side), and
mutation-checked by swapping the last two arguments, which it catches.

That is the third instance in two packages — WP-11.13 re-cut a source grep for
`">= int(COVERAGE * _eW * _eH)"` that went red on the fix to the very defect it guarded, and
two more before it. **A guard reading a literal cannot survive a rewording and cannot tell a fix
from a regression**, and the failure mode here is the milder one: it fails loudly on an
unrelated change, wasting the next reader's time rather than lying to them.

## VIII. What this package does NOT do

- **It does not put `edge_ft` on the plan record.** WP-11.3's rule is that the marks go on the
  record and the renderers derive nothing, and the stronger form of this fix would have
  `openings.place` write each opening's face at placement time. That is a plan-schema change and
  a placer change; the two renderers agree by contract today, which is the standard this file
  has been held to since WP-6.1.
- **It does not sweep the other exterior marks.** Item 3 of the question asked whether there is
  an eighth — the stoop, the chimney stacks and the elevation's own marks were not examined
  here. Doors and windows were, because those are what `derive_openings` owns.
- **It does not tag the shipped record.** Still `oq/the-parti-dissolved-its-own-dependencies`.
- **No new checker**; `TOTAL_CHECKS` does not move.
