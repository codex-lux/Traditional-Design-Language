# Structure

Wall thickness, bearing lines, span checking, storey heights, eave/ridge, and stair geometry — the layer between a solved plan (clear room dimensions, `build/geometry.py`) and a framed, dimensioned building.

```
python3 build/structure.py plans/tidewater-georgian-careful.json \
  --out plans/tidewater-georgian-careful.section.json \
  --svg dist/tidewater-section.svg --bearing-svg dist/tidewater-bearing.svg
```

## What this package adds, and does not touch

`build/geometry.py` places rooms at their clear (interior) dimensions and stops there — no wall thickness, no structural grid, no roof, as `docs/geometry.md`'s own "What this does not yet do" section says plainly. `build/structure.py` takes a solved plan and derives everything geometry.py deliberately does not attempt, without rewriting a single room rectangle: rooms keep their clear dimensions throughout, exactly as the hand-off brief instructs (*"extend the plan record so rooms keep clear dimensions while the footprint becomes outside-to-outside"*).

Five things come out of `build_section()`:

- **A wall-thickness lookup** (`wall_thickness()`) — reads the plan's own `declared.construction_type` against a new `construction/wall-assemblies.json` catalog (ten records: solid masonry two- and three-wythe, masonry veneer over frame, braced timber frame, balloon frame, platform frame, log, adobe, rammed earth, SIP), each with exterior / bearing-interior / partition thickness ranges and a bearing role. Falls back to platform-frame with an explicit note when nothing is declared — "unjudged is not passed" applied to structure, the same discipline `plan_check.py` already applies to a plan's room and style layers.
- **Wall lines and an outside-to-outside footprint** (`wall_lines()`, `outside_to_outside_footprint()`) — every exterior boundary edge plus every interior segment two placed rooms actually share, then the clear footprint grown by the exterior wall's own thickness.
- **Bearing lines and span checking** (`bearing_lines()`, `span_check()`) — an interior wall is bearing if it falls on the bay grid the parti was built from (timber-framed systems put posts, bents and bearing partitions on the bay lines by construction — `proportions/modules/timber-bay.json`'s own instruction), a partition otherwise. Each bay-to-bay clear span is then checked against either a light-frame joist member (`construction/floor-structure.json`) or the bay module's own documented 20 ft capacity for a hand-timber-framed style, and every span that fails is reported, not silently dropped.
- **Storey heights and roof heights** (`storey_heights()`, `roof_heights()`) — inverts `proportions/modules/storey-graduation.json`'s own ceiling-height rule (`ceiling = module - part*1.25`) to recover the storey (floor-to-floor) height every plan record's `floor_to_ceiling_ft` already implies, then a grade-to-eave and grade-to-ridge height using the style's own migrated roof-pitch constraint where one exists.
- **Stair geometry** (`stair_geometry()`) — rise, run, riser count and landing depth from `storey-graduation.json`'s own `stair_type` rule (risers = `ceil(storey_height_in / 7.25)`) and a conventional rise+2×run comfort formula for tread, checked against `groupings/stair-and-landing-core.json`'s hard landing rule and IRC's advisory riser maximum, using the stair-hall's own **solved** width from `geometry.py` — not an assumed one.

Every number here is advisory, the same discipline `schema/brief.schema.json`'s own `jurisdiction` field already states for code checks generally, and `construction/floor-structure.json` says for itself: this is "no silent pass" honesty at the structural layer, not a stamped calculation.

## `construction/`, a new top-level catalog

Two new files, sourced from conventional/typical construction data rather than a period authority — the same honesty split `schema/brief.schema.json`'s `jurisdiction` field already draws for code checks ("advisory and jurisdictional") is drawn here between the *proportion* packs (`proportions/modules/`, sourced from period treatises and measured survey) and this *assembly* catalog (sourced from typical modern construction figures, cross-checked against `elements/slots.json`'s own wall-thickness slot notes where one exists):

- `construction/wall-assemblies.json` — one record per `construction_type` (`elements/slots.json`'s own slot examples, transcribed exactly), each with exterior / bearing-interior / partition thickness ranges and a `bearing` role (`load-bearing-masonry`, `veneer-non-bearing`, `load-bearing-frame`, `load-bearing-solid`, `load-bearing-mass`, `load-bearing-panel`).
- `construction/floor-structure.json` — a `light_frame_joist_spans` table (2×8 through 2×12, two engineered I-joist sizes) for modern dimensional/engineered lumber, explicitly scoped to styles *outside* `timber-bay.json`'s applies_to list — see "What was found" below for why that scoping is load-bearing on the module's own correctness, not a stylistic nicety.

Neither catalog is validated against a JSON Schema file — `build/validate.py` only schema-checks `styles/*.json`, and no other `build/check_*.py` globs a new top-level directory by default, so adding `construction/` needed no schema-registration step. Both catalogs carry their own `authority` block on every record instead, marked `"strength": "conventional"`, matching this corpus's existing convention for data that is typical/illustrative rather than a rediscovered period rule.

## `build/render_section.py`, a new renderer

Two views, per the hand-off brief's own instruction — *"a section SVG rendered only from the record"* — meaning neither function re-opens a plan, re-runs `geometry.py`, or recomputes a number the section record does not already carry:

- **`render_section()`** — a vertical slice: grade line, each storey's floor line with its ceiling/storey/floor-structure-depth label, the eave, and the ridge (a simple triangle) where `roof_heights()` judged a pitch — or an explicit "RIDGE UNJUDGED" caption quoting the record's own note when it did not.
- **`render_bearing_diagram()`** — one plan-view panel per level: every wall line from `wall_lines()`/`bearing_lines()`, bearing walls drawn heavy, partitions drawn light and dashed, and any span that `span_check()` flagged drawn as a highlighted bar across the offending bay — the acceptance text's own case ("no 2×10 spanning 18 ft passes silently") made visible on the drawing, not just present in a JSON field nobody opens.

## What was found

Three real bugs, each caught only by actually running `build/structure.py` for the first time against the reference corpus and inspecting the raw output — not by re-reading the code. Each has a dedicated regression test in `tests/test_structure.py` rather than being fixed silently.

**1. The four exterior walls had their axis and position swapped.** `_shared_segment()` (and `wall_lines()`'s own interior-wall loop) uses the convention that axis `"x"` is a *vertical* wall at a given x-position, spanning a y-range, and axis `"y"` is a *horizontal* wall at a given y-position, spanning an x-range. The exterior-wall loop that seeds `wall_lines()` had this backwards: the S/N boundary walls (which are horizontal, at y=0 and y=H) were tagged axis `"x"`, and the W/E boundary walls (vertical, at x=0 and x=W) were tagged axis `"y"`. Concretely, on `tidewater-georgian-careful.json`'s 60×40.08 ft footprint, this planted the N wall's y=40.08 position into the **x**-axis break-point list `span_check()` uses to slice up x-direction spans — fabricating a bogus interior break point at x≈40 ft that does not correspond to any real wall — and planted the E wall's x=60 position into the **y**-axis break-point list, producing a completely out-of-bounds span from y=40.08 to y=60 on a building only 40.08 ft deep, which `span_check()` then dutifully (and wrongly) evaluated and reported as "ok" against an engineered joist. Fixed by correcting the axis/position pairing to match the convention `_shared_segment()` already establishes; `TestWallLinesExteriorOrientation` in `tests/test_structure.py` pins the corrected orientation and specifically asserts neither boundary wall's position leaks into the other axis's break-point set.

**2. `span_check()`'s hand-timber-vs-light-frame decision checked the wrong field against `timber-bay.json`'s `applies_to` list.** That list holds **style** ids (`"tidewater-georgian"`, `"colonial-revival"`, …) — the pack's own module note defines the bay as "the span the floor joists or the summer beam must make," a property of the framing tradition a *style* belongs to. The first version of `span_check()` checked `construction_type` (a wall-assembly id like `"solid-masonry-two-wythe"` or `"platform-frame"`) against that same list, which can never match — no wall-assembly id is a style id — so every plan, regardless of style, silently fell through to the light-frame joist table. This mattered concretely on `tidewater-georgian-careful.json` itself: that plan's own bays (up to 11.89 ft on one axis, 8.12 ft on the other) all happened to fit comfortably under both the light-frame table's largest member (24 ft) and the bay module's 20 ft cap, so the bug produced no visibly wrong *pass/fail* on the acceptance-example plan — but it was checking the wrong catalog against the wrong number system for a hand-timber-framed Georgian house, and would have silently accepted a 22 ft hand-hewn-joist span (light-frame's engineered-joist ceiling) that the bay module's own sourced note says a hewn joist cannot make. Fixed by keying `span_check()`'s `timber_framed` decision on the plan's **style** instead; `TestSpanCheckFramingBasis` pins both directions (a timber-bay style checked against the 20 ft module cap, a non-timber-bay style checked against the joist table) plus the acceptance text's own literal case (`test_no_2x10_spanning_18ft_passes_silently`).

**3. `graduation_check()`'s third/second-storey band was hand-transcribed wrong.** `storey-graduation.json`'s `height_proportion` rule carries four bands: second-over-first (0.78–0.92), third-over-second (0.70–0.88), attic-over-below (0.48–0.78, marked `judgment: true`), and ground-under-a-piano-nobile (0.60–0.85, an inverted special case). The first version of `graduation_check()` hard-coded `(0.78, 0.92)` for the first pair correctly but used `(0.60, 0.85)` — the *piano-nobile* band — for the second pair, instead of the actual third/second band `(0.70, 0.88)`. Fixed by reading the bands directly out of the pack's own `derived_rules` at call time (`[tuple(r["range"]) for r in pack["derived_rules"] if r["target_slot"] == "height_proportion"][:2]`) rather than re-transcribing them, so a future edit to the pack's own numbers cannot silently drift out of sync with a second, hand-copied version of them here. `TestGraduationCheck` pins the correct band pair directly against the pack file.

**A fourth item is a genuine, evidenced tension recorded rather than resolved — the same discipline WP-2.2's dining-room finding used.** `span_check()`'s style-based `timber_framed` decision (bug #2's fix) is architecturally correct for the acceptance-example plan — `tidewater-georgian-careful.json` is a masonry-walled Georgian house whose *floor* framing is still period hand-hewn joists, which is exactly what the pack's own applies_to list is describing. But running `structure.py` against the corpus's second reference plan, `plans/spec-builder-colonial.json` (style `colonial-revival`, which **is** in `timber-bay.json`'s applies_to list, but which declares **no** `construction_type` at all), surfaced the tension directly: that plan's own ground-floor bay comes out to 23.39 ft, which fails the 20 ft hand-timber cap — but a `colonial-revival` house, being a *revival* of the Georgian/Colonial appearance rather than a period building, is very plausibly framed in modern platform framing with dimensional or engineered lumber in real life, in which case a 23.39 ft span is well inside an engineered I-joist's 24 ft capacity and would pass cleanly. This corpus records no field that states the *floor framing method* independently of either the style or the wall's `construction_type`, and the two available signals can point different directions for exactly this kind of revival-style, light-frame-walled plan. Rather than pick one reading silently, `build_section()` now computes a `framing_basis` note whenever a timber-bay-applicable style meets an undeclared or declared-light-frame `construction_type`, stating plainly that the bay-module cap is being applied as the *pack's own style-level default*, not as a claim about this specific plan's actual framing — see `TestSpanCheckFramingBasis::test_build_section_flags_the_style_vs_construction_type_tension`. Resolving it properly would mean adding a field to this corpus that states framing era/method independently (e.g. a `hand_framed: true/false` flag on `wall-assemblies.json`'s `braced-timber-frame` record, defaulted false everywhere else) — not decided here, per this session's practice of not making corpus-wide-blast-radius judgment calls unilaterally.

## Verified against the acceptance criteria

Run against `plans/tidewater-georgian-careful.json`, PLAN-OF-ACTION.md's own named acceptance example:

- **Outside-to-outside footprint**: 62.58 × 42.66 ft, grown from the clear 60.0 × 40.08 ft footprint by the plan's declared `solid-masonry-two-wythe` construction's 15.5 in exterior wall (midpoint of the catalog's 13–18 in range).
- **Wall lines**: 29 lines on the ground floor (9 bearing), 22 on the upper (12 bearing) — four exterior plus every interior segment two placed rooms actually share.
- **Bearing-line diagram**: `dist/`-rendered via `render_bearing_diagram()`, heavy lines for bearing walls, dashed for partitions, verified visually via a cairosvg PNG render during this package's own development.
- **Section with eave/ridge heights consistent with the style's pitch constraint**: grade-to-eave 25.44 ft, grade-to-ridge 39.66 ft, at the midpoint (8.0:12) of `tidewater-georgian.c02`'s own migrated 7:12–9:12 constraint — `TestBuildSectionEndToEnd::test_tidewater_plan_section_eave_and_ridge_consistent_with_style_pitch` pins the pitch-consistency directly, not just that a number exists.
- **"No 2×10 spanning 18 ft passes silently"**: exercised both on the literal case (`test_no_2x10_spanning_18ft_passes_silently` — an 18 ft span is never reported as covered by a 2×10, which caps at 16 ft) and empirically on `spec-builder-colonial.json`'s own 23.39 ft ground-floor bay, which `span_check()` correctly flags as exceeding the (style-selected) 20 ft hand-timber capacity rather than passing it silently.

The Tidewater plan's own bays all come in under both the light-frame table and the timber-bay module cap, so **zero** spans are flagged on that specific plan — a genuine, checked pass (spans were actually computed and evaluated, `TestBuildSectionEndToEnd::test_no_span_over_capacity_passes_silently_on_the_careful_plan` confirms spans exist before asserting none failed), not an absence of checking.

A real, unresolved finding surfaced on this same plan while verifying the stair: the stair-hall's solved geometry (10.0 × 10.62 ft) cannot fit a single straight flight covering the ground storey's full 12.28 ft rise (21 risers, 200 in of run) without a landing longer than the room itself — `stair_geometry()` correctly reports this as a landing-rule violation rather than passing it silently. This is very plausibly a genuine defect worth a second look at this reference plan's own stair-hall sizing (see "What was deliberately not done" below on why this module cannot suggest a switchback in its place), not a bug in the check.

## What was deliberately not done

- **Only a single straight stair flight is modelled.** `stair_geometry()` computes one continuous run from storey floor to storey floor and checks whether the room can hold a landing at the end of it. A real stair taller than roughly 12–14 risers commonly switches back with an intermediate landing, which changes the room footprint the stair actually needs (roughly half the run, doubled in width) — not modelled here. The tidewater plan's own 21-riser flight (noted above) is exactly the case where this simplification produces a "landing too short" finding that a switchback stair would resolve differently; the finding is real and worth surfacing, but the fix (a winder or switchback geometry) is a materially separate piece of work.
- **Headroom is flagged as not independently verified.** `stair_geometry()`'s own `headroom_note` says so explicitly: the floor structure depth above a stair run (from `span_check()`) is not yet reconciled against the run's own rise to confirm the IRC's 80 in advisory headroom minimum is actually met at every point along the flight.
- **Roof FORM is out of scope.** `roof_heights()` produces only grade-to-eave and grade-to-ridge numbers for the section record, assuming a single ridge over the shorter footprint dimension — the common simple gable/hip case, and explicitly wrong for an L-plan, cross-gable, or hyphen-and-dependency massing, which the returned record's own `note` field says plainly. Hip vs. gable vs. gambrel form, ridge step-down between massing volumes, and dormers are WP-3.3's own work package.
- **Per-storey wythe step-down is not modelled.** `wall-assemblies.json`'s own `solid-masonry-three-wythe` record notes that a real masonry bearing wall commonly steps down a wythe at an upper floor (heavier at the base, lighter above) — this catalog reports one thickness per construction type for the whole building, not a per-storey schedule.
- **`wall_thickness()` reports one number for the whole building.** No per-room or per-wall override for a party wall, a chimney mass, or a bay window's own thinner enclosure.
- **Basements are not modelled.** `storey_heights()`/the grade-datum logic in `build_section()` only assigns a `grade_to_floor_ft` to storeys at or above the ground floor (`index >= 0`); a below-grade level is left with that field unset rather than guessed at.
- **The construction catalogs are not validated against a JSON Schema.** Consistent with the rest of this corpus's proportion/module packs, which also carry no schema file — `build/validate.py` only schema-checks `styles/*.json`.
