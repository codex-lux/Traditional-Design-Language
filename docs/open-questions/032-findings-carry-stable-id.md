# OQ 32 — findings carry no stable id

*Status: CLOSED 26 AUG 2026 · Raised in: From the workbench (WP-5.2, 25 Aug 2026)*

**CLOSED 26 Aug 2026 — findings carry a server-minted id built from what they are ABOUT, never from how they are phrased.** `build/plan_check.py`'s `Findings.add` mints an `id` from the layer, the room, and the rule or fault id where the finding has one, with an ordinal disambiguating within a group that has none. Verified unique across both shipped plans (111 and 142 findings, 111 and 142 ids) and readable — `fault:blank-wall-to-the-street`, `adjacency:powder#1` — which matters because it is what a citation will carry.
**One trap found while building it, and it is the same bug wearing a disguise.** `rule` carries an id on some layers and, on the adjacency layer, a whole paragraph of the rule's reasoning. Admitting it unconditionally produced ids with a paragraph of prose inside them — an id that embeds the very sentence it exists to be independent of. Only an id-shaped value is allowed into the key now.
The workbench prefers `f.id` and keeps its old `hash(layer|statement|room)` only as a fallback for a response from a server older than this change, with a comment saying why it must never go back to being primary. Four tests, one of which rewords a finding and asserts the id does not move — the regression stated as a test rather than as a hope. *Original entry follows.*<br><br>**OPEN — findings carry no stable id.** A validator finding is `{severity, layer, statement, room?, rule?, fix?}` — nothing to diff one run's findings against the next, cite from the rail, or animate appearing/clearing in the workbench's style-switch interaction. The app derives a client-side key from `hash(layer|statement|room)`, which works until a statement's wording changes, at which point every open row, citation and diff silently breaks. A server-side id (even the same hash, minted in `Findings.add`) would make findings first-class citable objects. Cost: one field on every finding; nothing existing reads finding identity, so it is purely additive. Surfaced by WP-5.2; worked around, not fixed.
