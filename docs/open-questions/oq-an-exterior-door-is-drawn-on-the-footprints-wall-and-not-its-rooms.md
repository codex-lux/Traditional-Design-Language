# oq/an-exterior-door-is-drawn-on-the-footprints-wall-and-not-its-rooms — the seventh layer that reads one rectangle

*Status: OPEN · Raised in: WP-11.13, the box that could not hold its own rooms (7 September 2026)*

**OPEN — both plan renderers draw an exterior door and its frame on the FOOTPRINT's wall rather
than on the wall of the room's own massing element. On a one-rectangle house those are the same
line and the whole corpus is unaffected; on a plan with a dependency the door is drawn in open
space, feet clear of the room it belongs to. WP-11.9 taught six layers about massing elements
and this is a seventh, in the file that draws the answer.**

## The measurement

Found by rendering the hand-tagged `tidewater-georgian-careful` that WP-11.13 made provable, and
looking at the sheet — which is the sixth package running that this technique has found
something nothing else did. Two exterior doors, each with its sill and swing arc, drawn north of
the whole building and attached to nothing.

The record is right and says so:

| door | room's own north face | drawn at |
|---|---|---|
| `backhall → exterior` (hyphen, y 12–30) | **30.0 ft** | 42.0 ft |
| `kitchen → exterior` (dependency, y 20–33.02) | **33.02 ft** | 42.0 ft |

`openings.place` seated both correctly on their own element's boundary — that is WP-11.9's
`_boundary_walls` teaching, and it works. The drawing throws the answer away.

## Where it is, in both spellings

`build/render_plan.py`, in `render()`:

```python
px, py = (p_, 0.0 if wl == "S" else H) if horiz else (0.0 if wl == "W" else W, p_)
```

`W` and `H` are the FOOTPRINT's width and depth. `_frame()` twenty lines above carries the same
two expressions (`Y(0 if wl == "S" else H)`, `X(0 if wl == "W" else W)`), which is why the sill
and the glazing line float with the leaf. `workbench/app/src/sheet/derive.js` has the same
construct, and its own docstring states it as the intended behaviour: *"plus exterior doors as
openings on the footprint edge."*

**The INTERIOR branch three lines up is already right**, and it is the model for the fix — it
takes the perpendicular coordinate from the room's own rectangle:

```python
at = (a["y_ft"] + a["depth_ft"]) if wall == "N" else a["y_ft"] if wall == "S" else ...
```

An exterior entry stores only `wall` and `at_ft`, a position ALONG the wall, so the drawing has
nothing else to read and derives the perpendicular coordinate from the only rectangle it has.

## Why it was not fixed in WP-11.13

The honest fix is to write the room's own face coordinate onto the exterior entry in
`derive_openings` — where `a` is already in scope — and have both drawings read it, which is
this corpus's standing rule that the marks go on the record and the renderer derives nothing
(WP-11.3). That means adding a key to `derive_openings`' output in BOTH spellings, and
`tests/fixtures/sheet_symbols/` holds the two to one contract by comparing that output against a
frozen `expected`. **That fixture is regenerated by solving** — `generate.py` calls
`geometry.solve(plan)` with no engine argument, so `auto`, so CP-SAT under a wall clock — and
`oq/the-frozen-fixture-is-regenerated-by-solving` records that regenerating it hands the reader
eight hundred lines of solver noise with the real change buried in it. Doing that inside a
package about element box arithmetic would be two things reasoned about as one, which is the
lesson WP-11.9 states in its own report.

## What must be ruled, or at least decided, before it is built

1. **Does the new field go on the exterior entry, or is it derived at draw time from the room?**
   The record-carries-it form matches WP-11.3 and WP-6.2 and costs a fixture regeneration. The
   derive-at-draw-time form costs nothing in the fixture and puts geometry back in two
   renderers, which is what the sheet-symbols contract exists to prevent.
2. **What does the frozen fixture become?** Its own README says a fixture generated by solving
   would pin the machine as much as the code, and its generator does exactly that. Any package
   touching `derive_openings`' output shape meets this, so it may be worth settling first.
3. **Is there an eighth?** This was found by looking at one sheet of one hand-tagged plan. The
   other exterior marks — windows, the stoop, the chimney stacks — should be swept against the
   room's own element rather than assumed correct because one drawing looked right.

Until then: **a multi-element sheet draws its exterior doors in the wrong place, and nothing on
the plate says so.** No plan in this corpus carries a `block` tag, so nothing shipped is
affected, and `tests/test_elements.py`'s two corpus hashes hold that.
