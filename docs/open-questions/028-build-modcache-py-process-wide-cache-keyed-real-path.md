# OQ 28 — `build/modcache.py`, one process-wide cache keyed by real path; every local `_mod()`/`_load()` now delegates to it. Steady-state `check()` 3.06 s → 0.31 s, `compose()` 30-40 s → 7-9 s, the full 291-test suite 3 chunks / ~12 min → one run / 2 min 24 s, restoring WP-0.3's "under five minutes" acceptance line. The profile turned out to understate the problem: a *single* `check()` was executing plan_check 16 times, geometry 8, structure 4, and roof/core/elevation/proportion_engine twice each, because the by-path loads are module-level and nest (elevation → plan_check + geometry + structure + roof + engine; roof → plan_check + geometry + structure; structure → plan_check + geometry; geometry → plan_check), so the whole tree was re-walked at every entry point rather than only `core._data()` going cold. Neither of the two fixes proposed below was taken: caching `core` at `plan_check`'s scope would have fixed one edge of that graph and left the other fifteen loads in place, and an mtime-keyed disk cache would have added a staleness class this corpus does not otherwise have. The delegation approach keeps the by-path convention exactly as it was — every script still runs standalone, every call site keeps its signature — and only stops the re-execution. Pinned by `tests/test_modcache.py` (5 tests, including a counter asserting a warm `check()` executes no module at all). The one behavioural change: a cached module is not re-executed, so a process that mutates a corpus file and re-loads in-process will not see the change — safe here because the mutation tests in `test_ontology.py`/`test_constraints.py` all run their checker as a subprocess, and `modcache.invalidate()` exists for anything that ever needs it. See `docs/reports/oq-28-module-cache.md`

See `docs/reports/oq-28-module-cache.md`.** Original entry follows.<br><br>**OPEN — `plan_check.py`'s `_load()` re-imports `mcp_server/core.py` fresh on every `check()` call, defeating `core._data()`'s own `@functools.lru_cache`.** Each fresh `importlib` module exec gets its own empty cache, so every `check()` call re-reads the whole corpus (styles, faults, kits, rooms, groupings — several hundred files) from disk. This predates this migration, but a smaller constraint payload kept it cheap enough that nobody had profiled it: with all 660 constraints now carrying `id`/`scope`/`test`, a single `compose()` call profiles at 30-40 seconds (up from whatever it cost before, not independently benchmarked pre-migration), and the full pytest suite no longer completes inside a 10-minute run. Nothing is wrong with any answer `check()` or `compose()` gives — every pinned test and both shipped plans' and both reference briefs' composer rankings were re-verified unchanged — this is a cost, not a correctness bug. Two contained fixes suggest themselves (cache the loaded `core` module at `plan_check.py`'s own module scope across `check()` calls within one process; or have `core._data()` itself cache to a file keyed on corpus mtimes) but both touch a loading pattern (`_load()`/`_mod()`, fresh `importlib.util.spec_from_file_location` per call) used the same way across several files as a deliberate isolation convention, and picking one wasn't this package's call to make unilaterally. See `docs/reports/wp-1.1-remaining-families-migration.md` for the profile that found it.
