# OQ 36 — the compose job registry pins the service to a single replica, and serializes compose across all users

*Status: OPEN · Raised in: From deployment (25 Aug 2026)*

**OPEN — the compose job registry pins the service to a single replica, and serializes compose across all users.** `workbench/server/jobs.py` holds `_JOBS = {}` in process memory (30-minute TTL) and runs its work on `ThreadPoolExecutor(max_workers=1)`. Deployed, that has two consequences the deployment doc records and the platform config currently works around by keeping replicas at 1: a second replica cannot see the first's jobs, so a caller polling `/api/jobs/{id}` after a load-balanced hop gets a 404 for a job that is running fine elsewhere; and because the pool is one worker wide, a second user's compose waits behind the first's rather than running beside it. Neither is wrong at the scale this is being deployed for — a handful of people trying it — and both are the correct simple choice for a local instrument, which is what WP-5.2 built. The question is what to do when it stops being true, and the options differ in kind rather than degree: (a) leave it, cap replicas at 1 forever, and treat compose as a single-user operation, which is honest but puts a hard ceiling on concurrent users; (b) widen `max_workers` and keep the registry in memory, which fixes the queueing but not the replica problem and makes the memory cost of concurrent 250-candidate searches a real question; (c) move job state to something shared — Redis or Postgres — which fixes both and is the first thing in this project that would genuinely need a database, having spent its whole life without one. Worth noting the corpus itself never enters this: it is read-only and identical in every replica. Only *job* state is at issue. Surfaced by the deployment package; nothing changed on the strength of it beyond documenting the replica constraint.
