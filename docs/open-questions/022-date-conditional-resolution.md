# OQ 22 — No date-conditional resolution

*Status: RESOLVED · Raised in: Structural, unresolved*

**RESOLVED — No date-conditional resolution.** `applies_when.date_range` existed and was populated (49 dated variant records corpus-wide as of WP-1.3), but nothing selected on it. For a style spanning 1700–1800 — 12/12 to 9/6 to 6/6 sash, fanlights after 1780, butt hinges after 1775 — a resolved kit had to present all the options rather than the ones current at a stated date. **Executed in WP-1.3:** `build/resolve_kit.py --date YEAR` filters every slot's variant list to what `applies_when.date_range` permits at that year (inclusive bounds; an undated variant applies at any date), in the CLI table, the `--slot` detail view, and `--json` (where every variant instead gets an explicit `in_period` boolean rather than being filtered, so a downstream consumer can choose). Nothing excluded is silently dropped — the count and ids of what got left out are always printed alongside what's shown. Real case: `tidewater-georgian`'s `window_head_masonry` correctly flips from `segmental-gauged-arch` to `gauged-flat-arch` across the 1750 threshold the kit's own note names as a dating tell. Only `applies_when.date_range` on **variants** is handled — no kit data currently puts `date_range` on a `parameters` entry (checked corpus-wide), so that path is unbuilt and untested; if a future style needs a date-conditional parameter value rather than a date-conditional variant choice, `eval_parameters` will need the same treatment.
